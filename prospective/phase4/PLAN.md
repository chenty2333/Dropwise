## 1. 问题与统计单位

- **Q1：** 三个分支各确认多少问题？分别报告 B1/B2/B3/M1，以及只有 M1 看到的问题。相同根因跨操作、复用模式、层级只算一个问题，另列发现它的路径。
- **Q2：** 环境、制造挂起、观察者、编写/运行、初判、Claude 复核、对照和用户裁决各花多少时间？逐单元记录代码量、修改次数和卡点，不能只报 runner 时间。
- **Q3：** 执行 AI 与另一独立 Claude 会话的分诊一致率是多少？用户裁决了几次，分别属于什么分歧类型？一致不等于正确，不能把双 AI 一致率写成人工验证准确率。
- **Q4：** 三个选择漏斗分别淘汰了什么？样本的下载量、排名、协议族分布如何？只能描述所选样本，不估计整个生态的缺陷率。
- **Q5：** 当前正式版本上的确认问题中，哪些上游已知、哪些可能新发现？旧版回溯结果不进入本期分母。

**目标单元**是 `(生态, 客户端族, 复用模式, 操作)`。每种复用模式最多两个操作：第一个可用于长寿命会话的状态调用，再选一个普通完整请求；没有合适的状态调用就只选一个。初始化后句柄不能存活的握手不单列。不是把一次请求里的每条协议消息都算一个目标。

同一 crate/package 的池化和直接句柄场景分开计单元，但**跨分支仍按客户端族聚类**；manager、二进制实现附属包、同源 fork 不算独立客户端。同时报告单元数、客户端 crate/package 数，manager 数不充数。Python 内部再分 pool/direct，绝不把 Python pool 和 Rust pool 混成一个推断分母。

## 2. 三个分支与选择规则

### 2.1 Rust 共用的用量门槛（先判门槛，后判 API/可行性）

**客户端 crate 或其专用 manager 的近 90 天下载量至少 1,000 次。** 两者任一达到即可，不能把多个低用量包装的下载相加；不能用通用池 bb8/deadpool/mobc 的下载为客户端背书。manager 和客户端必须有公开的对应关系。crate 级下载是所有版本合计，不冒充所选版本的下载量。

理由：1,000/90 天约每天 11 次，是排除几乎无人使用目标的最低实际用量线，不是“广泛生产使用”的证明。该值在本次修订的取消实验之前写明，两个 Rust 分支、条件目标和配对表全部同一标准；不因结果、点名例子或数量不足而改变。

数据源是 `prospective/candidate-scan/universe.csv`：2026-10-18、815 行，按 `downloads_90d` 排序；**208 行达到门槛，607 行未达到**。这是反向依赖加人工种子的便利 frame，不是 crates.io 全体。对低下载的 manager 行可合并至已过线的客户端族，但不新增独立目标。没有数字的候选标“未核实”，不能当作过线。完整逐行判断在 `rust-selection.csv`，包括重新判断的排名 1–69；不能沿用“phase 3 已审，所以不用重看”。

沿用已测排除集合：tokio-tungstenite、sqlx-postgres、sqlx-mysql、redis、tokio-postgres、bb8、bb8-memcached、deadpool-memcached、lettre、deadpool-postgres、async-nats、moka；phase 3 八个客户端族（含合并包装）；neo4rs；diesel-async。已测客户端不能靠换 manager、直接句柄或改版本重新算“新 crate”。

### 2.2 Rust 池化分支（R-P）

异步客户端；公开 API 提供池或已有专用 manager；池上每条借出的连接顺序请求/回复；服务端有本地 Docker 方案，或简单公开协议的进程内模型。用一个池、一条并发连接；不能把内部多调用方 dispatcher 强行串行调用后称为顺序连接。

### 2.3 Rust 直接句柄分支（R-H）

用户在目标 future 之外持有**长寿命连接句柄**，依次发送多个请求；只丢弃借用该句柄的目标 future，幸存者继续在**同一个句柄**上调用。不是断线重建，不是退池再借，也不是仅仅复用一个内部含池的高层 Client。

从全部过门槛行重判，特别是排名 1–69 的无池拒绝项以及 81 的 tokio-modbus、91 的 async-smtp、166 的 async-pop。已测排除集合不变。能公开直接操作连接的双模式客户端两种场景都列出；事务/游标等短命子对象不自动算第二种连接句柄。未核实的模式不算已纳入。

### 2.4 顺序协议与多路复用的统一边界

看复用单元的公开 API，而不是看到协议有编号就排除：IMAP tag、Modbus TCP transaction id、MongoDB responseTo、Bolt qid 在**一条物理连接最多一个请求往返**的路径上只是关联/终止标记，可纳入；若 API 允许多个调用方在同一连接上并发并由 dispatcher 路由回复则排除。HTTP 限 HTTP/1.1；HTTP/2、gRPC、AMQP channel、MQTT event loop、CQL stream、LDAP message id dispatcher 不纳入。WebSocket 底层 transport 没有明确请求/回复契约也不纳入，不再写“因为没有池”。

只读 README、公开 API 签名/示例、依赖清单与服务端文档进行选择，**不读被测客户端取消相关实现**。公共 trait 适配可以用成熟现成工具；不为老 runtime 引入新兼容工作流。

### 2.5 Python 前瞻分支（P）

- **可复现总体：** hugovk/top-pypi-packages 的 **2026 年 9 月下载量月榜**。2026-10-19 下载；响应 `last_update = 2026-10-01 12:40:51`、`source = ClickHouse`，15,000 行。旧 URL 名含 `30-days`，但上游当前采集程序按上个自然月查询，不能写成截至 10 月 19 日的滚动 30 天。
- 原响应保存为 `python-top-pypi-2026-09.json`。获取方式、原 URL、排序与边界见 `targets.md`；公开 PyPI 元数据的版本/摘要/API 来源随逐行筛选保存在 `python-selection.csv`。不安装或执行下载的包。
- **本期判断前 1,500 名**，按 `download_count` 降序（并列按名称），不在凑满某个客户端数后停。第 1,501–15,000 名为**未审**，不是排除。这是本次草稿资源边界，不声称早于查看榜单就预注册；不为点名目标向后补种子。
- Python 不把 Rust 的 90 天数字换算成月数字；采用**月榜前 1,500 名**的用量规则。两生态用量门槛不是等价的，必须分别报告。
- 纳入：有 asyncio 客户端 API；复用的是一条顺序请求/回复的字节流，或按 §2.4 明确限制到无并发路由的路径；池化或可直接持有连接；服务端可在本机 Docker 运行。HTTP 可用本地 Docker HTTP/1.1 端点，不依赖外网账号。仅转发已有客户端的 wrapper 合并；线程池执行同步 I/O 的 async 包装不当作原生 asyncio 客户端。
- 先用公开包元数据剔除明显非客户端，再对可能的网络客户端查 README/公开 API；每行给理由和来源，不读取消实现。**SQLAlchemy：已经在 python-retro 中测试。**
- 测**当前正式版**，不测 beta/RC/dev、不回退到已知有问题的旧版本。`targets.md` 列本次 PyPI 查询的正式版本；未来获准执行前重新查询，若更新，先在未看到任何结果时修订名单和 API 判断，再固定该次版本。依赖/池包同样记录实际版本。
- redis-py、aiohttp 的旧版在回溯研究中已测；用户要求的当前版可列本期，但必须标为“已接触该客户端的当前版扩展”，与真正首次接触的 Python 包分列，不冒称全盲新目标。SQLAlchemy 不重复纳入。motor 与 pymongo 属同一驱动族，选择当前原生 async API，不能当两个独立目标。

## 4. 四层级与覆盖

四层级的**语义**相同，运行时机制不同：

| 层级 | Rust | Python |
|---|---|---|
| B1 | drop 目标后结束，只看 panic/超时/obligation | cancel 目标并 await 清理完成后结束；预期 CancelledError 正常，其他异常/超时单列 |
| B2 | 同池或同句柄、同参数重试，只判 Ok | 同复用单元、同参数重试；无异常返回算成功，不查具体值 |
| B3 | 同池或同句柄换一个同类操作，只判 Ok | 同左，不查返回值 |
| M1 | `explore_observed(Expect::Atomic)` | 现有 `dropwise_py.explore_observed(expect=Expect.ATOMIC)` |

M1 幸存者必须碰被取消操作的**同一 key/行/邮箱等对象**并做有副作用的操作；观察包含具体返回值、同连接读回和独立观察者的服务端效果。观察者绕过被测池、句柄和延迟代理。pre/post 各两次，同侧不一致记 Unknown；退化观察 pre==post 要写清覆盖不到什么。只有残留字节而无用户后果的 M1-residue 单列，不算 Q1。

### 4.1 Rust 配置

沿用 phase 3：`Flavor::MultiThread { workers: 1 }`、`Race::Immediate/AfterWake`、`max_cancellations=1`、`max_runs=64`、单场景超时 20 s、`Settle { tokio_time: Duration::ZERO, ..default }`，每项 3 轮。每目标一种 Pending 手段，四层级共用。池大小 1 不保证物理连接不变：库可能正常关闭/更换连接，必须记录重用/重连，不能阻止合法自愈。

### 4.2 Python 配置与已有引擎

只复用 `research/python-retro/dropwise_py/`，不修改其中任何文件，不扩核心框架。该引擎以纯 Python `_PyTask` 的 `_Task__step` 计数目标任务让出事件循环的次数 K，在第 k 次后 `Task.cancel()`；不用对协程手工 throw。不是源码 await 计数，也不等同 Rust poll/AfterWake。

以后每项 3 轮，每轮每个计划 3 次重复，超时参数 15 s，pre/post 各两次；先各层独立测 K，记录计划集合，只比较同轮共同且 realized 的计划。**不能凭各层 pending#k 数值相同就认定是同一语义位置**；没有运行时/API 阶段对应证据时，只做层级级汇总，不宣称逐点增益。Rust 3 轮与 Python 每轮重复数不同，不能合并原始 trial 数比较效率。

取消后 await 目标终止，让 `finally`/`except` 完成；不照搬 Rust settle 或固定 sleep，不在目标与幸存者间加“等旧回复到齐”的等待。shield 派生后台任务未必随目标结束：只能观察公开完成信号并报告未完成，不能声称已经静止。场景的幸存者、观察者和清理不得吞掉 runner 的 `CancelledError` 后继续工作；捕获业务异常时须让控制取消传播。python-retro §8.2 的 P2 是池连接泄漏加测试侧吞取消，不是事件循环同步卡死。设每个 trial 的外部进程硬截止 60 s，同时覆盖吞取消和真正同步阻塞；硬截止是 incomplete/覆盖缺口，不能直接算确认问题。这里仅规定未来 runner 行为，本轮不写 runner。

### 4.3 正式运行前的检查（本轮不执行）

每条路径先声明 `Atomic` 适用的契约及允许的关闭/重连行为；不把合法部分进度或文档允许的拒绝复用直接计为缺陷。无法建立契约时记无法评价，不临时放宽判定。三次无取消连续使用证明 reuse；目标至少实际挂起一次；pre/post 校准和独立观察者有效。直接句柄同时确认对象身份和服务端连接标识；不能用重连代替同句柄后继请求。若库自行关闭连接，记录同句柄调用的真实错误，不能在幸存者前偷偷新建。

每层每轮必须报告 K/计划集合、attempted、realized、unrealized、Unknown、baseline_errors、超时/硬截止、未覆盖/排除点、pre/post 是否退化、实际连接重用/重连。现有 Python 引擎可能为 unrealized trial 也给观察判定；**汇总须显式过滤 unrealized/Unknown 和基线失败**，不能直接拿 `violations()` 长度当有效发现数。`Report.exhaustive` 也不是完整覆盖证明。基线失败或 K=0 时写“无法评价”，不能写“干净”。

## 5. 执行方式、分诊与 Q3

### 5.1 检测与修改边界

未来每客户端族一个隔离执行上下文，只给指南、目标版本/模式/操作类别、输出路径；不给其他目标结果、特定历史 bug 的暗示或复核结论。已经接触过的 redis/aiohttp 单独标记，不能事后抹掉先验。

运行前写 `SCENARIO.md`（操作、复用单元、Pending/挂起手段、观察、pre/post、reuse）；之后只修 harness，记录是否已看结果。改变操作/模式/观察/挂起手段须作为新场景版本重跑全部层级；不得只跑失败层级。环境、代码、观察者、判定、Claude、对照的实际成本分开记录；跨模式共享的 setup 只算一次，不把共享成本遗漏或重复收取。

### 5.2 执行 AI + 独立 Claude，用户裁决分歧

1. 执行 AI 将完整场景、日志、公开契约和初判写入 `TRIAGE-AI.md`。
2. **另一个 Claude 会话**只拿场景、原始日志、操作定义、公开文档和对照材料，**不看执行 AI 的结论/理由**，独立写 `TRIAGE-CLAUDE.md`。对照证据里的诊断性结论也须去掉，不隐去运行事实。执行 AI 在交卷前也不能看到 Claude 的结论。不是让本会话换个口吻再评一次；本轮不启动 Claude 会话。
3. 双方提交后再对账。结论三类：confirmed / contract-external / harness error；证据不够另记 unresolved，不强迫三选一。只有有用户可见后果、明确契约依据并有消除后果的补丁/配置对照，才计 confirmed。双 AI 一致也不能代替对照。
4. 用户只裁决**不一致、unresolved、安全/披露或预算例外**。保留原始独立结论和用户最终裁决，不为提高一致率改写初判。有分歧的候选在用户裁决前不计确认问题；一致项仍须满足 confirmed 的证据条件。

**Q3 主分母：** 有有效违反、且两个 AI 都交卷的目标单元；两者的类别集合及其对应候选问题（含 unresolved）完全相同记一致，漏掉同类的另一个问题也算不一致，每单元只记一次，多个计划不充样本。报告 `一致单元/双评单元` 及单元级结论组合交叉表；另给已配对候选问题的 3×3 类别混淆表、unresolved/未配对项单列；未交卷不进入一致率，但列数量/原因。另报 crate/package 聚类的一致性，不将多操作视为独立。

**用户裁决表：** 请求次数、已完成次数、未决次数、分钟数；类型固定为确认↔契约外、确认↔harness、遗漏/额外问题、证据/覆盖不足、根因/层级归因、其他。一个请求含多个分歧时记一个请求、多条类型，不把次数和类型条数混用。Q3 不是“AI 与人一致率”。零发现单元不进 Q3 主分母，但 Claude 检查覆盖是否足够，并计入 Q1 的所有选中/已完成分母。

### 5.3 对照、已知问题与披露

分诊阶段才允许读取消实现；记录检测/分诊读过什么。补丁在被测依赖的副本或隔离安装中，检测构建不带补丁；不修改 Dropwise 或 python-retro。配置/调用方 guard 对照也可，但必须说清改变了什么。

## 6. 预算与停止规则

以下是**未来执行估计**，不是本轮实测成本；AI 小时是各会话主动工作墙钟之和，不是并行后的日历时长。共享环境只归一次，Claude 独立计时。

| 分支 | 执行 AI（环境+全部四层级+初判）估计 | Claude 复核估计 | 分支 AI 上限 |
|---|---:|---:|---:|
| R-P：11 主 + 3 条件 | 主名单 18–25 h，条件使用剩余额度 | 主数 11×15 min = 2.75 h；条件另 0.75 h | 40 h |
| R-H：12 主 + 2 条件 | 主名单 12–18 h（共享已有环境，不重复收费） | 主数 12×15 min = 3 h；条件另 0.5 h | 30 h |
| P：27 主 + 6 条件 | 主名单 18–25 h，条件使用剩余额度 | 主数 27×15 min = 6.75 h；条件另 1.5 h | 45 h |
| 全局对照、对账、汇总 | 5–8 h（含约 6 个问题×45 min 对照的排期假设） | — | 5 h 额外额度；其余需从分支余额调剂 |
| **总计** | **执行与汇总 53–76 h** | **主数 12.5 h；条件全过 15.25 h** | **120 AI 小时，总额优先于分项上限** |

因此主名单预计 **65.5–88.5 AI 小时**，条件全过和困难环境会向总上限靠近。不能把 120 h 写成预计必用的时间。每单元执行上限 2.5 h；每客户端族 setup 上限 4 h（跨模式共享）；每个候选问题对照上限 90 min；Claude 每单元上限 30 min。各项不是另行追加额度，任一全局/局部预算先到就记 incomplete，不自动扩期。不能在全局汇总额度用尽后继续做新对照。

**用户时间：预计 3 h、硬上限 6 h**（原草稿是 20 h）：计划/结果确认各约 30 min、约 6 次分歧裁决×15 min=90 min、少量双 AI 一致项抽查约 30 min。6 次是排期假设，不是限制或实测；第 7 次也如实记。每次裁决最多 30 min；超预算仍未决的记 unresolved，用户可自行决定是否追加，不让用户逐目标独立重做分诊。日历估计 4–6 周，按每周约 15–20 AI 小时安排；不据此授权后台持续工作。

**停止/替换：** 固定的是选定名单，不按发现数停止。条件检查在任何取消结果之前做；失败不补位。主目标失败也保留在漏斗/成本中，不为填满数字换低下载目标。单元、环境、对照、Claude 或用户上限达到即记未完成；总预算达到则停，不降低层级或轮次。若新估计比总预算高出 25%，在继续前交用户确认。安全停止按 §5.3。本轮保持未冻结，不能执行上述检查。

## 8. 局限

- 高下载不等于用户数；Rust 90 天下载与 Python 自然月下载、两个便利 frame 都不等价；前 1,500 的 Python 边界会遗漏边界外客户端，不能声称完成生态普查。
- 顺序字节流选择偏向本方法；多路复用/事件流的排除不是安全结论。单连接、单服务端配置、单挂起手段不能代表生产部署。
- **Python 只枚举目标任务的运行时让出点，不包括同步回调内的状态转移**（python-retro RESULTS §7、§8.3），也不保证覆盖 native I/O 或后台子任务内部。不能把每个源码 await、所有调度交错或所有库状态转移都称为已枚举。
- K 随网络/调度变化，unrealized 不能算通过；批量回复、池的 peek/重连可掩盖窗口（§8.1、§8.4）。没有固定 settle 不证明后台工作已静止。
- Python `Task.cancel()` 可被捕获、shield 或 uncancel；异步清理不同于 Rust 同步 drop。超时异常也不是纯取消；本期不把 timeout-BEGIN 注入混入挂起点前瞻结果。
- asyncio 超时可能因场景吞取消或真正同步阻塞而失效，须外部硬截止，缺口仍是缺口。python-retro §8.2 已确认的是前者，不作为同步阻塞的实证。现有引擎用 CPython 私有 `_PyTask/_Task__step`：未来先验证实际 CPython 正式版本上的计数有效，不支持就记环境未完成，不在本期改引擎/补兼容层。记录 CPython 版本，不外推其他实现/版本（§8.5）。
- pre==post 只能约束观察到的幸存者性质，不能证明取消操作是否回滚。Unknown、基线失败和硬截止不算确认违反，也不是阴性证据。
- 两 AI 可能共享训练偏差；独立会话不等于统计独立/人工真值。当前版 redis/aiohttp 有既往接触；用户只裁决分歧也可能漏掉两 AI 一致的错误。
- 条件和静态可行性不等于本机启动成功；全部版本、连接复用和挂起覆盖仍待另行授权的 setup 核实。没有动态数据，不宣称任何新问题或安全结论。
