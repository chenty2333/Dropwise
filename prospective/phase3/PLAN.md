# Phase 3：模板对未知目标是否更有效

> 状态：**已冻结（2026-10-19）**，见同目录 `FREEZE.txt`。之后只能在 `AMENDMENTS.md` 里追加修订（写明日期、原因、是否在看到结果之后），不能改本文和 `targets.md`。
> 背景：research/literature/FOLLOWUP.md 的“Gemini 第四轮”一节。RESCAN 与 scan-clients 的结果都是事后的，或者目标是按清单、带着先验挑的，不能回答“面对事先不知道有没有问题的目标，这套方法是否更有效、成本多高”。

## 1. 问题

- **Q1：** 在按冻结规则选出的、事先没测过的目标上，“幸存者 + 允许集合”模板（M1）比三个简单取消测试层级（B1、B2、B3）各多发现多少确认的问题？
- **Q2：** 每个目标的适配成本是多少，花在哪里（搭环境、制造 Pending、写观察者、判定）？
- **Q3（次要）：** 残留字节检查在多少目标上可用，额外发现了什么？

## 2. 选目标的规则

总体：`prospective/candidate-scan/universe.csv`（815 个 crate，crates.io 2026-10-18 快照），按近 90 天下载量降序。

**纳入**（只看 README、文档和公开 API，不读取消相关的实现代码）：

1. 异步客户端，被复用的单元是一条**按顺序一问一答的字节流**，没有请求编号或流编号这类多路复用（HTTP/1.1 连接、MySQL/MongoDB 单连接等）；
2. 连接会被复用：自带连接池，或有 bb8 / deadpool / mobc 的 manager；
3. 服务端能在本机 Docker 里跑起来，或能用进程内假服务器替代（只限协议简单、公开规范明确的情况）。

**排除：**

- 已覆盖的目标：tokio-tungstenite、sqlx-postgres、sqlx-mysql、redis、tokio-postgres、bb8、bb8-memcached、deadpool-memcached、lettre、deadpool-postgres、async-nats、moka；
- 扫描器线索 diesel-async（已单独动态测试，单列一层，不计入主结果）；
- 只是转发到已纳入客户端的包装 crate（例如同一个池的不同 manager），合并成一个目标。

按顺序取前 **8** 个符合条件的 crate。逐个判断的理由和最终名单见 `targets.md`（与本文一起冻结）。

**每个 crate 最多两个目标操作**，按 `docs/choosing-targets.md` 清单顺序选：

1. 第一个建立会话状态的调用（事务、checkout、握手、`USE`/`SET` 一类），没有就跳过；
2. 一个普通的一问一答请求。

## 3. 四个层级（同一个场景骨架，只换取消之后测什么、怎么判）

- **B1 只看取消本身：** 目标被取消后场景直接结束。用 `dropwise::explore`，只要不 panic、不超时、没有 Obligation 泄漏就算通过。
- **B2 原地重试：** 取消后，通过同一个池或连接，用**完全相同的参数**再做一次同一个操作；返回 `Ok` 就算通过（超时算失败）。
- **B3 换一个操作：** 取消后，通过同一个池做一个**不同的**同类操作（换 key、换查询、换收件人）；只看是否返回 `Ok`，不检查值。
- **M1 模板：** `explore_observed(Expect::Atomic)`。幸存者通过同一个池做一次有副作用的操作，再由独立观察者确认（单独的连接、服务端 API）。判定值**不含**残留字节。
- **M1-residue（只用于 Q3）：** 能用 `dropwise::net::Proxy` 的目标，另跑一版把幸存者开始前的残留字节加进观察值。它会把“连接错位但用户结果正确”也报出来（RESCAN 6.6 与 6.9 的区别），所以它的违反单独统计，不计入 Q1，除非分诊确认了用户可见的后果。

四个层级用同一个场景骨架、同一个 Dropwise 配置，都在每个 Pending 处取消目标操作，区别只在取消之后测什么、怎么判。配置相同：`Flavor::MultiThread { workers: 1 }`、`races = [Immediate, AfterWake]`、`max_cancellations = 1`，每项重复 3 次。

允许的 Pending 制造手段：服务端延迟（`SLEEP` 一类）、大负载、慢的进程内假服务器、`dropwise::net::Proxy` 的扣住回复模式（`Proxy::start_with` 的 `reply_delay`，真实时间延迟，只适合 `Flavor::MultiThread`）。同一个目标的四个层级必须用同一种手段。

检测阶段不允许修改被测 crate。分诊时为了确认一个问题，可以在被测 crate 的副本上打补丁做对照（`[patch.crates-io]`，补丁放进实验目录）。

M1 的发现先与 B3 逐计划比较：M1 抓到、B3 没抓到的每个计划，都要写一句低层级为什么看不到（返回值相同、仍在事务里、回复都是成功码等）。

## 4. 判定与记录

- 违反先人工分诊，结论分三类：**确认的问题**（能说明后继者看到了什么，并且有一个能消除它的补丁或配置对照）、**契约外行为**（库的文档明确不保证，或者属于协议本身不原子）、**测试框架错误**。只有第一类计入 Q1，按层级分别计数：一个确认的问题，算作“被某层级发现”的条件是该层级在至少一轮里报出了它对应的计划。
- 由于 `Flavor::MultiThread` 使用真实时间，计划数可能在轮与轮之间浮动；逐计划比较层级时，只在同一轮内比较。
- 每个目标记录：场景代码行数（按 B1–B3/M1 分开，不含共享的环境代码）、工时，以及工时大致花在四类事情上的比例。
- 结果写进 `RESULTS.md`，零发现也照样报告。

## 5. 预算与停止规则

- 每个目标最多半天。超时就记为“未完成”和原因，不延长。
- 如果发现可能涉及安全的问题（例如下一个使用者读到别的请求的数据），先停下这个目标，只在本地记录，不写进任何会公开的文件，交给项目负责人决定披露方式，再继续下一个。
- 不向上游提交任何东西；上报由项目负责人在看完结果后决定。
