# Phase 3 结果：模板对未知目标是否更有效（2026-10-19）

> 冻结的方案与目标清单见 `PLAN.md`、`targets.md`（sha256 与 `FREEZE.txt` 一致）。所有偏离与修订见 `AMENDMENTS.md` 第 1–16 条，其中第 16 条是复核时对 mongodb MG1 的改判。
> 逐目标的细节、逐轮数字和原始日志索引：HTTP 客户端见 `RESULTS-http.md`，数据库客户端见 `RESULTS-db.md`。本文只做汇总；两者冲突时，以本文和 AMENDMENTS 第 16 条为准。
> 运行入口：`bash prospective/phase3/run-http.sh`、`bash prospective/phase3/run-db.sh`。

## 一句话结论

8 个按冻结规则选出、事先没测过的目标全部做完，每个目标都跑满了四个层级、每级 3 轮：

- **确认的问题有 1 个：** mysql_async 直接持有的 `Conn`，一个查询被取消后，下一个查询静默返回被取消那个查询的结果。**只有 M1（幸存者 + 独立观察者 + 两条基线）抓到；B1、B2、B3 都没抓到。**
- **契约外行为 1 个：** mongodb 事务的第一条命令被取消后，事务留在服务端。只有 B2（原地重试）抓到。驱动的 README 明确不保证丢弃驱动 future 之后的行为，因此不计入 Q1（AMENDMENTS 第 16 条）。
- **其余 6 个目标零发现：** hyper-util、reqwest、pingora、isahc、awc，以及 clickhouse-arrow。mysql_async 和 mongodb 经由各自连接池的路径也是零发现。HTTP 这一侧有阳性对照，排除了"观察器失灵"导致的零。

## Q1：各层级多发现了多少确认的问题

| 层级 | 确认的问题 |
|---|---:|
| B1 只看取消本身 | 0 |
| B2 原地重试 | 0 |
| B3 换一个操作 | 0 |
| M1 模板 | **1**（mysql_async MY2） |

MY2 为什么低层级看不到：被取消的 `SELECT 12345` 的结果留在连接上，下一个查询（不管是重试还是换一个查询）把它当成自己的结果读走，返回 `Ok`。B2、B3 只检查 `Ok`，所以通过；只有比较返回值的 M1 看出 `SELECT 67890` 拿到了 12345。补丁版（让已标记 `disconnected` 的连接拒绝新命令）加上调用方检查 `is_disconnected()` 后，3 轮全部为 0。

**样本只有 8 个目标、1 个确认的问题，只能作描述，不能据此说"M1 比 B3 强多少"。** 它与回溯实验（RESCAN 6.7，消融阶梯）的方向一致：会报错或卡住的问题，简单测试就能抓到；静默的错误结果只有 M1 能抓到。

## 从 MG1 学到的：幸存者要碰同一个对象

MG1 是唯一一个 B2 抓到、M1 没抓到的情况。被放弃的事务锁住的是 `_id = mg1` 这个文档：B2 用完全相同的参数重试，正好撞上；而 M1 的幸存者写的是另一个文档，独立观察者读的也是自己的文档，所以什么也没看到。

这说明 M1 强不强，取决于幸存者和观察者的设计，并不天然包含 B2。以后写场景时，幸存者除了做一次自己的操作，还应该**碰一下被取消操作碰过的那个对象**（同一个 key、同一行、同一个文档）。这条经验应该补进 `docs/choosing-targets.md`。

## Q2：成本

| 目标组 | 共享环境 | 每个目标的适配 | 实际用时 |
|---|---|---|---|
| HTTP（5 个） | 626 行（进程内 HTTP 服务器 175 行、harness 389 行、运行脚本 62 行） | 32–41 行 | 每个约 30–45 分钟（含共享部分，约 75 分钟） |
| 数据库（3 个） | 各自的容器与 `Env` | 每个层级 15–60 行 | 20–50 分钟 |

时间比例是执行者按工作内容估的，不是计时器读数：**搭环境 25–55%、写观察者 10–35%、判定 15–30%、制造 Pending 5–20%。** 成本的大头在搭环境和写观察者上，这和之前"判定之外的场景成本降不下来"的观察一致。用时是由一个 AI 执行者完成时的工时，不能直接换算成人工工时。

## Q3：残留字节

- 8 个目标都能用 `dropwise::net::Proxy` 做残留检查。
- **只在 MY2 看到残留**：58 字节，就是被取消查询的结果，与 M1 的发现是同一个问题。其他目标的残留全部为 0。HTTP 的阳性对照里残留是 262252 字节，说明检查本身是有效的。
- **残留检查没有带来 M1 之外的新发现。**

## 环境发现（不计入 Q1）

clickhouse-arrow 0.2.1 无法和 ClickHouse 24.8.14.39 通信：在服务端 revision 早于 54470 的回退分支里，客户端强制使用分块模式，服务端不认识这种分块数据包，报 `Unknown packet`。一行补丁就能确认根因。主结果因此改在官方的 25.5.2.47 上跑（AMENDMENTS 第 7 条）。这是兼容性问题，与取消无关，可以单独报给上游。

## 局限

- 8 个目标，1 个确认的问题：只能作描述，不能做统计推断。
- 纳入规则（单字节流、会被池化复用）本身就偏向我们的方法擅长的类型。
- 选目标、写场景、分诊都是同一个项目的人和 AI 执行者完成的，没有盲法。MG1 的改判是复核时、看到结果之后做的（AMENDMENTS 第 16 条）。
- HTTP 一侧没有补丁版（没有发现）。只测了 HTTP/1.1、明文、单一负载大小；hyper、reqwest、isahc 写请求体的过程在内部任务里，方法看不到那部分的挂起点。
- 用时来自 AI 执行者，比例是估计值。

## 上报状态

- mysql_async MY2：**已上报（2026-10-19）**：issue [blackbeam/mysql_async#412](https://github.com/blackbeam/mysql_async/issues/412)，修复 PR [#413](https://github.com/blackbeam/mysql_async/pull/413)。PR 用一个 drop guard 记录“routine 在完成前被丢弃”，之后的命令返回 `ConnectionClosed`；不能直接检查 `disconnected`，因为 routine 会合法地嵌套（`clean_dirty` 在外层 routine 里回滚事务）。新回归测试在 master 上失败、修复后通过。

- clickhouse-arrow 兼容性：可以单独上报，优先级低。
