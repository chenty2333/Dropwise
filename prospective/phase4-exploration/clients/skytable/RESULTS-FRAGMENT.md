## Operations and reuse unit

Setup creates a fresh space/model per scenario run through a direct observer
connection: `create space <unique>`, `create model <space>.kv(id: string, v: uint64)`,
insert `("k", 0)`. Skytable has **no transactions** and no separate auth round trip,
so no transaction was faked.

- Target: `update <space>.kv set v = 1 where id = "k"`.
  - pooled: the target future is `pool.get()` + update (checkout/validation inside
    the target; pool size 1). This is deliberate and recorded in `SCENARIO.md`.
  - direct: one long-lived `ConnectionAsync` outside the target; target only borrows it.
- B2: same update, same row/value, same handle/pool.
- B3: `select v from <space>.kv where id = "k"` on the same handle/pool.
- M1 survivor: update the **same row** to `v = 7`, then select it back; observer =
  separate direct `ConnectionAsync` (bypasses pool and proxy).
- Pending: `dropwise::net::Proxy` with `reply_delay = 50 ms` on server→client chunks.
- Config: `races=[Immediate,AfterWake]`, `max_cancellations=1`, `max_runs=64`,
  `scenario_timeout=20 s`, `Settle{tokio_time:0, real_time:0, watchdog:10 s}`.

- pooled `#0@1:Immediate`: `before=Ok(0) write=Ok(()) own=Err("row not found (empty response)") visible=Ok(7)`;
  pre=`Ok(0)/Ok(())/Ok(7)/Ok(7)`, post=`Ok(1)/Ok(())/Ok(7)/Ok(7)`.
- pooled `#0@2:AfterWake`: `before=Ok(1) write=Ok(()) own=Err("row not found (empty response)") visible=Ok(7)`.
- direct `#0@1:AfterWake`: `before=Ok(1) write=Ok(()) own=Err("server error 6") visible=Ok(1)`.
- direct `#0@1:Immediate`: `before=Ok(0) write=Ok(()) own=Err("row not found (empty response)") visible=Ok(7)`.

B2 (Ok-only) sees `retry=Ok` in 2/4 pooled plans and 1/2 direct plans; the others are
`Err(server error 6)`. B3 values are `Ok(0)` (stale, target not applied),
`Err(server error 6)` (server-side illegal packet) or `Err(row not found)`
(stale Empty reply consumed as a select result).

The user-visible phenomenon is one root cause: the cancelled `query()` future
leaves its reply (or part of it) on the same connection; the next request reads
that stale reply as its own. Pooled mode adds the bb8 validation query between
target and survivor, which shifts rather than repairs the association; pooled
also produced server error 6, consistent with a request/response boundary being
split. The server row itself is intact (observer `visible=7` in every M1 line)
and a fresh connection reads/writes it correctly.

## Triage and classification

- **Confirmed client-side defect (protocol/response association after a dropped
  query future), one root cause.** The cancelled `query()` leaves the reply (or a
  prefix/one packet of it) on the connection; the next request through the same
  handle — bb8's validation query in pooled mode, or the survivor's update in
  direct mode — consumes it as its own. Consequences: survivor `own` read fails or
  returns a stale value while the independent observer sees the correct row
  (`visible=7`), and the server sometimes returns error 6 (illegal client packet),
  indicating a packet boundary was split, not just a logical ordering mistake.
- Contract status: skytable 0.8.12 public docs/README describe `query` as one
  request/response and offer a pool, but state no cancellation guarantee and no
  reset/recovery action. The defect is therefore a real user-visible reuse
  failure with a silent contract, not a documented "not guaranteed" case.
- Known/new: **not verified**. Upstream issue search (skytable/client-rust,
  cancel/drop/pool/reuse) was not done inside the timebox; no issue is claimed.
- Patch contrast: **none**. No dependency-copy patch was attempted in the
  timebox. A minimal repair would need to discard/mark-broken the connection when
  a query future is dropped (and the pool manager to honour it); skytable's
  public API exposes no reset, so this cannot be done by a scenario or by the
  `bb8` configuration alone.
- Pre/post: calibration equal within each side (2 samples), different across
  sides (`pre_equal=true post_equal=true pre_post_equal=false`). A cancelled
  target that the server applied (`before=1`) is compared with post; it is not
  itself a violation. All reported M1 violations have a broken survivor/own read,
  not merely a different target-progress side.

## What was not covered

- No modbus or async-pop work (lead timebox; separate families).
- No upstream issue search, no patch/rejection-path contrast.
- No pool size >1, no pipelines, no TLS, no server restart/crash, no multi-thread
  workers >1, no `After(Duration)`/reschedule races, single client version.
- Only loopback and a disposable local server; no vendor/production Skytable.
- Generated cases were run pooled only; direct generated cases were not run.
- Login/auth as a target: not applicable (handshake-only auth, no request).
- The 50 ms proxy delay is the only Pending mechanism; server-side stalls and
  network partition were not modelled.
