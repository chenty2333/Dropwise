# Round-2 IMAP summary (2026-10-21)

Round 2 is a separate experiment, not an extension of the round-1 denominators.
All values below are from the files in `logs/round2-*`; see
`logs/round2-environment.txt` for the two containers, image digest and
toolchain. Published = async-imap 0.12.0. Patched = the dependency copy with
`patched/append-continuation.round2.patch`.

### Does retry SELECT restore the session?

- **Published, retry first:** yes for command alignment. Every realised retry
  SELECT returned `Ok`; the following APPEND, SEARCH, FETCH and REST observer
  all succeeded on the same Session and same TCP connection. But the returned
  `Mailbox` is not clean: at `@1` cuts `flags_len=10` and
  `permanent_flags_len=12`; at `@2` cuts `flags_len=5` and
  `permanent_flags_len=12`. The normal values are 5 and 6.
- **Published, APPEND first:** no. APPEND fails immediately (`Err(Append)`)
  and leaves the server waiting for the APPEND literal. The subsequent retry
  SELECT is consumed as literal bytes: it times out at ~2.0 s, then SEARCH also
  times out and FETCH is not attempted. The observer sees only the seed.
- **Patched, APPEND first:** yes. The patched APPEND drains the abandoned
  SELECT responses, finds `+ OK`, writes the literal and succeeds; the retry
  SELECT then returns `Ok` with clean 5/6 flags, and SEARCH/FETCH/observer all
  succeed. This removes the order-dependent wedge.
- **Patched, retry first:** still duplicates the flags. The patch is only in
  APPEND; the retry SELECT still uses `parse_mailbox`, which merges the
  abandoned SELECT's FLAGS/PERMANENTFLAGS into its own.

Timing ranges (realised runs): published retry-first retry 101-144 ms, APPEND
184-236 ms; published reverse APPEND 0-92 ms, retry SELECT 2000-2001 ms, SEARCH
2000-2002 ms; patched reverse APPEND 145-286 ms, retry 91-144 ms, SEARCH 92-95
ms.

### Duplicated flags: client accumulation, not a server defect

The raw transcript of a published retry-first run shows the retry SELECT
(`A0004`) reading the abandoned SELECT's FLAGS/PERMANENTFLAGS and its stale
`A0003 OK`, then its own FLAGS/PERMANENTFLAGS and `A0004 OK`. The server never
sends a duplicate FLAGS list. `parse_mailbox` starts from
`Mailbox::default()` and uses `.extend()` for FLAGS and PERMANENTFLAGS, so the
two lists accumulate. `Mailbox.flags` and `.permanent_flags` are public
`Vec<Flag>` fields: the duplicates are user-visible as length/content, although
membership tests are unchanged. This is a client-side metadata defect triggered
by the abandoned SELECT, not an independent server defect, and it is not counted
as a B2 violation because B2 judged only `Ok`.

### B2 flags after the APPEND patch

The APPEND patch does not touch SELECT. Across the patched B2 rows, every
realised `@1` cut still returned 10 flags/12 permanent flags, and every
realised `@2` cut returned 5 flags/12 permanent flags. The duplication persists
exactly as in the published build; the patch neither creates nor removes it.

### B3 / M1 after the APPEND patch

- B3: published 10 realised cancellations, all `Err(Append)`, observer 0;
  patched 10 realised cancellations, all `Ok`, observer 1. The patch removes
  the B3 APPEND failure in all 10 realised cuts. Patched B3 rep 3 generated only
  two plans (one Pending observed); both succeeded.
- M1: published 12/12 realised, 12/12 Neither (representative:
  `append=Err(Append), search=Err(Timeout), fetch=Err(Timeout), observer=seed
  only`). Patched 12 plan observations, 8 realised and 4 baseline, all 12 Post
  (`append=Ok, search=Ok(1), fetch=Ok(survivor), observer=seed+survivor`);
  violations=0, neither=0. The four baseline rows are not counted as recovered
  cancellations; they are realisations that did not happen.

| fake own-tag NO before `+` | `Err(Append)`, 40 ms | `Err(Append)`, 40 ms |

The patched stale-SELECT transcript shows stale `* FLAGS`, `* EXISTS`,
`* RECENT`, UIDVALIDITY/UIDNEXT/UNSEEN/PERMANENTFLAGS and stale `A0002 OK`
skipped, then `+ OK`, the literal, and `A0003 OK [APPENDUID ...]`. The patched
stale-reject transcript shows the same drain, then `A0003 NO [TRYCREATE]`.
There is no infinite spin in any case; the only unbounded-looking case is a
stale `+` that is protocol-indistinguishable from this APPEND's own `+`, which
the caller's 2 s timeout ends in both builds.

## 4. Patch regression tests and upstream checks

- Published 0.12.0 + injected tests: **10 passed, 3 failed**. The three failures
  are the stale-SELECT, stale-other-tag-NO and stale-other-tag-BAD cases; all
  fail with `Err(Append)`. Upstream tests with the round-2 tests skipped:
  **73 passed, 0 failed**.
- Patched copy: **86 passed, 0 failed** (73 upstream + 13 round-2).
- `cargo fmt --all -- --check`: **0** for both patched and published copies.
- `cargo clippy --all-targets`: **0** for both; 5 unique warnings in each and
  an empty warning-set diff (the warnings are pre-existing in 0.12.0).
- Patch is the round-1 loop, unchanged in behavior, with comments and tests.
  It follows PR #142's tag-first discipline for LOGIN (saved diff
  `logs/round2-pr142.diff`), but APPEND's own tagged Done is an error because
  no literal was sent.

## 5. SEARCH on an unselected mailbox (separate defect)

Published and patched behave identically:

```text
before SELECT: search = Ok(0), raw="seqs=[]", 92 ms
server log:   Command 'SEARCH' not valid in this state AUTHENTICATED
after SELECT:  search = Ok(0), raw="seqs=[]", 51 ms (genuine empty result)
```

GreenMail rejected the first SEARCH with BAD; async-imap's `parse_ids` ended
silently at the matching tagged response and returned `Ok(empty)`. This is not
the APPEND defect and is not counted in the ladder. It is reproduced minimally
with no cancellation; see `logs/round2-*-search-unselected*`.

## 7. Limitations

- GreenMail only; response chunking is not controlled beyond the 50 ms proxy.
  The `@1`/`@2` split is the observed plan set, not a guaranteed protocol
  boundary.
- Plan counts vary between repetitions because a target can complete before the
  planned Pending. Unrealised plans are excluded from effect claims and shown
  in the table.
- The patch handles stale tagged/untagged responses and EOF before `+`, but a
  stale `+` cannot be correlated with a command in IMAP (the continuation is
  untagged). A cancelled APPEND continuation therefore still requires a
  reconnect or a protocol-level recovery primitive; this patch is not one.
- The patch does not fix `parse_mailbox` accumulation. Retry SELECT after a
  first-Pending cut remains metadata-contaminated.
- `NO`/`BAD` before `+` is collapsed to `Err(Append)`; it is prompt (51-52 ms)
  but loses the status detail.
- After `+`, `check_done_ok_from` still checks status before tag, so an
  unrelated tagged `NO`/`BAD` between `+` and this APPEND's completion could be
  reported as this APPEND's failure. The round-2 suite did not produce that
  ordering; it is a source-level limitation, not an observed GreenMail result.
- The round-2 patch is a dependency-copy triage change, not an upstream fix;
  it has not been reviewed by async-imap maintainers.
- No TLS, pipelining, multiple in-flight commands, or other IMAP servers were
  tested. The round-2 harness still uses one Session exposed outside the target
  future, as in round 1.
