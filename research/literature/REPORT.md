# 借三十年测试先例，补齐 Dropwise 的判定短板

Dropwise 最值得投入的低垂果实，不在“在哪里取消”，而在“取消之后怎么判、什么时候判”。在“在哪里取消”这一侧，Dropwise 按第 k 个 Pending 枚举取消点，已经和 Abrahams 2000 年的异常注入计数器、SQLite 的 OOM 循环、Linux `fail-nth`、CHESS 的 iterative context bounding 是同一套做法。这些工具各自配套的自动判定（oracle）和观察时机，却一直没被搬到 Rust future 的 drop 上。来自不同社区、互相不知道对方的三个部件，可以直接拼成一个基本不用手写不变式的默认 oracle。第一个是由 baseline 派生的允许集合：settle 后的状态必须属于 {操作前, 操作后}，来源是 C++ StrongCheck、SQLite“完成或完全回滚”、Witcher、Jepsen 的 `:info`。第二个是用静止判定代替固定 settle 窗口：Go `testing/synctest`、Trio、OCaml Eio、Cats Effect、TigerBeetle VOPR 各自独立收敛到这个做法。第三个是相对 baseline 的孤儿任务计数：goleak 在 Uber 的单元测试中找出 857 个既有泄漏。这三样在 Tokio 里都有现成原语（baseline 运行、paused time 的 auto-advance、`RuntimeMetrics::num_alive_tasks`），笔记估计各需 S–M 工作量。它们分别对准当前已知的三个弱点：条件要在读过修复之后才写得出来、立即观察在已修复代码上误报，以及只有恰好持有 `Obligation` 的泄漏才能被看到。第二梯队是让更多现有测试“有 Pending 可切、能零改动接入”，包括 Pending 制造器、确定性自检与覆盖断言、`cargo [patch]` 式的 CancelSan，以及 NonDex 式 baseline-first 差分。第三梯队是新的 plan 维度和省成本的手段。需要先说清楚：以下所有建议都**没有在 Dropwise 上实现或验证**。所谓“证据强”，只表示该机制在原领域有量化成果，不表示它对 Rust 取消一定有效。另外两点会影响优先级：Tokio 文档化的 cancel-unsafe API 做成模型库，收益上限有限，真正没人覆盖的是 futures combinator；futurelock 是一个与 drop 取消正交、生态里还没有工具的新 bug 类。

> 阅读约定：带 `([来源](URL))` 的句子是研究笔记中有一手或二手来源的事实。标“（推断）”的是笔记或本报告的推导，没有经过实验。工作量按 S ≈ 1–3 天、M ≈ 1–3 周、L ≈ 月级统一换算（五份笔记原先的刻度不一致，见“证据边界”一节）。

## 四个分别发明的部件，拼出一个不用手写条件的 oracle

用户说的“人类注意力盲区”在这批材料里有很具体的形态：同一个想法在不同社区各自做了一遍，但没有人把它们组合起来用到“future 在 await 点被 drop”这件事上。笔记检索到的 Rust 取消测试工具里，Hyperactor 和 futures-testing 只测单个 future，Asupersync 要求换运行时，async-rust-lsp 只做 `select!` 左侧的名单匹配。**没有一个工具复用既有集成测试，在 Tokio `select!`/`timeout` 处系统地注入取消** ([Hyperactor](https://github.com/meta-pytorch/monarch/blob/main/hyperactor/src/testing/cancel_safe.rs); [futures-testing](https://github.com/conradludgate/futures-testing); [Asupersync](https://github.com/Dicklesworthstone/asupersync); [async-rust-lsp](https://github.com/rgbkrk/async-rust-lsp))。RustConf 2025 上 Rain 关于取消的演讲也没有提到任何测试工具 ([sunshowers](https://sunshowers.io/posts/cancelling-async-rust/); [LWN](https://lwn.net/Articles/1036924/))。

**第一个部件是“允许集合”oracle。** Abrahams 的 `StrongCheck` 在注入失败前复制被测值，捕获异常后断言副本与原值相等；外层循环让失败点依次落在执行路径上的每一个可能抛出点 ([Boost: Exception-Safety in Generic Components](https://boost.org/doc/libs/1_34_0/more/generic_exception_safety.html))。SQLite 在 I/O 和崩溃测试后要求“事务要么完整完成，要么完全回滚” ([How SQLite Is Tested](https://sqlite.org/testing.html))。Witcher 把“有崩溃”和“无崩溃”两条执行做输出等价比较，一条参照假定操作已提交，另一条假定已回滚，**在 20 个 PMDK KV 存储中找到 47 个正确性 bug（其中 36 个是新的）** ([Witcher SOSP'21](https://www3.cs.stonybrook.edu/~dongyoon/papers/SOSP-21-Witcher.pdf))。Jepsen 把超时的操作标为 `:info`（可能生效也可能没生效），并指出能确定没生效的操作应标为 `:fail`，这样检查更快、检出也更多 ([Jepsen: checking correctness](https://cljdoc.org/d/io.jepsen/generator/0.1.2/doc/checking-correctness))。Dropwise 已经有 baseline 运行和按 Pending 边界枚举的 plan，所以只差一个用户提供的 `observe()` 快照函数，就能把“半完成态”的检测从手写不变式变成自动比较：settle 后的快照 S 必须属于 {S_pre, S_post}（推断）。这正好打在 Dropwise 的主 bug 形状上，也就是“await 前 take/pop/自增，await 后恢复或提交”。OSDI'22 的取消实证研究也提供了旁证：156 个取消 bug 中**超过 20% 是取消后的清理有缺陷，其中 80% 涉及堆数据**；最常见的修复是释放资源、让被修改的数据失效或回滚，而原本正确的释放例程在取消时被短路了 ([Sethi et al. OSDI'22](https://www.usenix.org/system/files/osdi22-sethi.pdf))。

**第二个部件是静止判定。** Go `testing/synctest` 的 `Wait` 会一直阻塞，直到 bubble 内其他 goroutine 全部“持久阻塞”，即只能被 bubble 内其他 goroutine 唤醒；mutex、网络 I/O 和系统调用明确不算。所有 goroutine 都持久阻塞时，时钟跳到下一个能唤醒某个 goroutine 的时刻；如果没有这样的时刻，就判死锁 ([pkg.go.dev testing/synctest](https://pkg.go.dev/testing/synctest))。Trio 的 `wait_all_tasks_blocked`、`MockClock(autojump_threshold)` ([Trio testing](https://trio.readthedocs.io/en/stable/reference-testing.html))，Eio mock backend 的自动推进时钟加死锁检测 ([Eio](https://github.com/ocaml-multicore/eio))，Cats Effect `TestControl.isDeadlocked` ([TestControl](https://typelevel.org/cats-effect/docs/core/test-runtime))，是另外三个独立先例。TigerBeetle VOPR 在 safety 阶段之后切换到 liveness mode：把故障概率设为 0，最多跑 `ticks_max_convergence` 个 tick 等待收敛，并且**只有在 `cluster_recoverable` 时不收敛才算 bug** ([vopr.zig](https://github.com/tigerbeetle/tigerbeetle/blob/main/src/vopr.zig))。Tokio 已经具备其中一半：时间暂停且运行时无事可做时，时钟会自动推进到下一个定时器，有 `spawn_blocking` 工作时则不推进 ([tokio::time::pause](https://docs.rs/tokio/latest/tokio/time/fn.pause.html))。

**第三个部件是孤儿任务检查。** goleak 在测试结束时检查残留 goroutine，用 `IgnoreCurrent` 对基线做差分，内部按指数退避重试（1µs 起翻倍，上限 100ms，最多 20 次）([goleak options.go](https://raw.githubusercontent.com/uber-go/goleak/master/options.go))。Uber 在单元测试中用它发现了 **857 个既有泄漏，并在一年内阻止约 260 个新泄漏** ([arXiv 2312.12002](https://arxiv.org/abs/2312.12002))。Rust 这边的对应点在于：drop `JoinHandle` 只会 detach，不会取消任务，所以 `tokio::spawn` 重新引入了令牌式生态里那种“取消没传到”的问题（推断，依据 [Yosh Wuyts](https://blog.yoshuawuyts.com/async-cancellation-1/) 对 detach 语义的描述）。`RuntimeMetrics::num_alive_tasks` 在 spawn 时加一、任务退出时减一 ([RuntimeMetrics](https://docs.rs/tokio/latest/tokio/runtime/struct.RuntimeMetrics.html))。拿取消运行和同一 plan 的 baseline 在 settle 后比较这个数，就是单元测试版的 goleak（推断）。Dropwise 目前只有当泄漏的任务恰好持有 `Obligation` 时才看得到这类问题。

**第四个部件是“规格允许的扰动”这一论证。** 它不是 oracle，但决定了误报能否讲得清楚。NonDex 只在规格欠定的 API 上随机探索合法行为，并且只报告“不扰动时通过、扰动后失败”的测试。它在 8 个项目中找到 21 个新 bug，提交的 13 个 PR 被接受了 12 个，75 个失败中有 74 个被二分到单个调用点 ([NonDex FSE'16](https://mir.cs.illinois.edu/gyori/pubs/nondex.pdf))。Tokio 生产环境本来就会因为 coop budget 在任意资源上返回 Pending ([tokio::task::coop](https://docs.rs/tokio/latest/tokio/task/coop/index.html))，`select!` 也默认随机挑选先 poll 的分支 ([tokio::select!](https://docs.rs/tokio/latest/tokio/macro.select.html))。所以 Dropwise 额外制造 Pending、再让竞争分支就绪，属于规格允许的扰动（推断）。这句话可以写进 README，回答“为什么报出来的失败该算在代码头上”。

把四者合起来，就是笔记里反复出现的组合：“取消 → 静止 → 状态 ∈ {pre, post} → 无孤儿任务 → 只报告 baseline 稳定通过的场景”。笔记在各自的检索范围内没有发现任何工作把它们合用于 Rust future 的 drop 取消。这是“未检索到”，不是“已证明不存在”。还有一组同构关系可以直接用于定位和文档：Lincheck 的 `promptCancellation`（已 resume 但还没运行时取消）就是 `Race::AfterWake` ([Lincheck options](https://kotlinlang.org/docs/lincheck-operation-execution-options.html))；Kotlin 为解决“取出元素后被取消而丢失”加了 `onUndeliveredElement`，这就是运行时版的 `Obligation` ([Kotlin Channel](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.channels/-channel/))。两者都是 Dropwise 设计在 Kotlin 生态里独立出现过的外部印证。

## 不让用户写不变式的 oracle 族

前三项（{pre, post}、结果-效果一致性、取消后重试）在笔记里被归纳为同一个族：**取消后的可观察结果必须属于由 baseline 派生的允许集合**，允许集合由调用上下文决定（推断）。调用方放弃操作时，允许集合是 {S_pre, S_post}，对应 strict linearizability 的“pending 操作在截止前生效，或者根本不生效”。调用方会重试时，允许集合是 {S_final_baseline}，对应 Ramalingam & Vaswani 的 failfree idempotence：存在重复请求和失败时的行为，应与不存在它们时不可区分 ([POPL'13](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/popl38-ramalingam.pdf))。后台任务会收尾时，在静止点检查，对应 durable linearizability ([arXiv 2208.11114](https://arxiv.org/pdf/2208.11114))。笔记建议把这三种情况做成一个枚举 `Expect::{Atomic, RetryEquivalent, EventuallyAtomic}`，用户只选上下文，不写条件。这一点的意义在于它**直接回应“条件是读过修复后才写的”这一评估弱点**：允许集合来自 baseline，而不是来自对 bug 的了解（推断）。

同一组快照还能顺带产出效果分类（推断，笔记未找到先例）。对第 k 个 Pending 的 plan，S_k = S_pre 记为“已回滚”，S_k = S_post 记为“已提交”，其他情况记为“半完成”。在正确的代码里，随 k 递增，结果序列应是单调的 `pre…pre post…post`，翻转点就是不可撤回点。翻转点之后如果调用方看到的是 Cancelled，而调用上下文又会重试，就必然产生重复。这样，“可逆 / 幂等 / 已提交”的分类和“提交早于不可撤回点”的检测，都不需要用户标注。

这个族有两个已知的坑，笔记之间是一致的。第一个是很多 I/O 操作只能满足 basic 保证（`read` 已经消费了部分字节），如果全局要求 strong，会重演“立即检查误报”的问题，所以必须允许按 target 声明保证级别。Abrahams 的三级保证（basic / strong / no-throw）正好对应 Dropwise 现有的不变式加 obligation、cancel-safe 和“不可取消，必须 spawn” ([Abrahams 2000](https://boost.org/doc/libs/1_34_0/more/generic_exception_safety.html))。第二个是快照里的非确定性噪声，例如时间戳和 HashMap 顺序。便宜的解法是借 DIDUCE“从严到松”的思路，把同一 plan 的 baseline 跑两次，自动屏蔽在两次 baseline 之间就不同的字段（推断）([DIDUCE](https://cs.fit.edu/~pkc/id/related/hangal-icse02.pdf))。

用户已经有顺序模型时，可以再往前走一步。被取消的转移在 proptest-state-machine 的参照模型上分叉成 {未应用, 已应用} 两个参照状态。顺序情形下不需要搜索，因为 Dropwise 每次运行的取消数很少，`:info` 操作带来的指数爆炸基本不会出现（推断）([proptest-state-machine](https://docs.rs/proptest-state-machine/^0.1.0); [Jepsen](https://cljdoc.org/d/io.jepsen/generator/0.1.2/doc/checking-correctness))。Elle 的“唯一追加值让读结果自证历史”也可以用在模型 sink 上：每条消息带 obligation id，sink 记录追加历史，丢失、重复、乱序都能自动推断 ([Elle](https://arxiv.org/abs/2003.10554))。对没有模型的用户，只挖静止点上的守恒类不变式（如 `x + y == 常量`、`len(a) == counter`）是“半个”低垂果实。只用单个输入的 baseline 会学到过拟合的常量，所以只保留关系型模板（推断）。

## 何时观察：静止点、瞬时与持久

早观察误报有一个有原则的解释：“obligation 最终被处理”是 liveness 性质，有限窗口内只能得出 false 或 inconclusive。Bauer 等的三值 LTL 运行时验证给出了这个口径 ([Bauer, Leucker, Schallhart TOSEM 2011](https://research.uni-luebeck.de/en/publications/runtime-verification-for-ltl-and-tltl/))。落到 Dropwise 上（推断）：“dropped unresolved”属于 safety 违例，可以立即判定；“outstanding after settle”只有到了静止点、并且不再有任何未来事件时，才能从 inconclusive 升级为 false。也就是说，Dropwise 现有的两类泄漏应该采用不同的观察策略。

笔记推荐的观察算法（推断）分几步。取消后驱动运行时到第一个静止点 Q1，判据是无可运行任务、无 blocking 工作、下一个定时器超出视界。在 Q1 检查 safety 类问题。然后允许时间推进，到达下一个静止点 Q2，如此往复，直到 obligation 表和快照在连续两个静止点上不变（不动点），或者到达视界。用不动点而不是“没有定时器”作判据，是为了容忍周期性心跳任务。视界的默认值可以从 baseline 自适应得到，即 baseline 到达不动点所需的虚拟时间乘以一个常数。还有一个副产品：“已经静止、没有未来事件，但某个 obligation 的 owner 仍然阻塞”可以直接判为“滞留/死锁”，不必等 watchdog。这正是 futurelock 和 lost-wakeup 类 hang 需要的判决。

实现风险都在 Tokio 一侧。Tokio 没有公开 API 可以查询 current_thread 运行时是否空闲或者下一个定时器在什么时刻，笔记**没有确认**有这类 API，只能通过 auto-advance 的时间跳变、`yield_now` 探针加 `num_alive_tasks` 间接探测，或者依赖 `tokio_unstable`。多线程 flavor 下没有可靠方法区分 worker 是在 park 还是卡住了 ([tokio #6696 镜像](https://hub.harborframework.com/tasks/abundant/tokio-rs__tokio-6696))，所以只能维持 inconclusive。在这之前，有两件便宜的事可以先做。一是窗口敏感性自检：同一 plan 用 T 和 2T 各跑一次，结论不同就降级。依据是 Luo 等的研究：在用 async wait 解决的 flaky 测试里，约三分之一用固定延迟强制顺序，作者建议改变这些延迟来暴露问题 ([Luo et al. FSE'14](https://huang.isis.vanderbilt.edu/cs8395/paper/flakytest.pdf))。二是把 `real_time` 改成 goleak 式的退避重试。

## plan 怎么选、预算多少、能给出什么保证

Dropwise 的 Notify lost-wakeup 只有多时序探索才能找到，io_uring fd 泄漏则用“第一个 Pending 取消 + 100ms settle”就够了。PCT 的 bug depth 框架恰好能解释这两个结果（推断）：PCT 单次运行找到深度为 d 的 bug 的概率不低于 1/(n·k^(d-1)) ([Burckhardt et al. ASPLOS'10](https://people.cs.rutgers.edu/~sn349/papers/asplos2010.pdf))；AfterWake 比 Immediate 多一个“已唤醒但还没被 poll”的约束，深度加一。SCTBench 在 49–52 个真实 bug 上发现：**大多数 bug 在 bound 1–2 内就能暴露，朴素随机比 preemption bounding 找到的更多** ([Thomson et al. TOPC'16](https://www.doc.ic.ac.uk/~afd/papers/2016/TOPC.pdf))。Lu 等的研究中，96% 的并发 bug 只需要强制两个线程之间的某个偏序 ([Lu et al. ASPLOS'08](https://www.cs.columbia.edu/~junfeng/08fa-e6998/sched/readings/concurrency-bugs.pdf))。这些结果共同支持“c=1 穷尽、c≥2 分层采样”作为默认值。分层的顺序是先选 target，再选 boundary，最后选 timing，这样可以避开 POS 指出的“朴素随机游走偏向步数多的分支” ([POS CAV'18](https://www.cs.columbia.edu/~junfeng/papers/pos-cav18.pdf))。在这种分层下，报告可以打印“若存在单取消 bug，R 次都没命中的概率 ≤ (1−p)^R”，其中 p ≥ 1/(|targets|·K_max·|T|)。这个界是笔记推导出来的，不是文献结论。至于“单次取消就能覆盖大多数取消 bug”，**目前没有文献支持**，需要用 G0 的 22 个案例自己统计。

“哪些时序值得跑”和“哪些失败开发者会认”是同一个问题。Fray 在 Kafka、Lucene、Guava 的 2,664 个现有测试上，POS/SURW 各让 360 多个测试失败，rr chaos mode 只有 5 个。但作者承认，对抗性时序（例如 sleep 10 秒早于另一线程的任何进展）会产生“现实中不太可能”的调度，有些开发者因此不愿修 ([Fray arXiv 2501.12618](https://arxiv.org/pdf/2501.12618))。TSVD 用 near-miss（冲突访问相距很近）挑选注入点 ([TSVD SOSP'19](https://6826.csail.mit.edu/2020/papers/tsvd.pdf))，NodeRacer 用 happens-before 排除不可行的事件推迟 ([NodeRacer](https://users-cs.au.dk/~amoeller/papers/noderacer/paper.pdf))。合起来的建议（推断）是给每个违例打标签：`Immediate`/`After(0)` 对上真实 30s timeout 标为“对抗”，baseline 中 target 完成时刻与竞争者就绪时刻接近的标为“现实”，竞争者就绪依赖 target 先完成的标为“不可行”。默认只让前两级导致 `assert_cancel_correct` 失败。

Dropwise 当前没有覆盖、加起来成本很低的时序和来源维度有这几项。RFD 400 列出的取消来源里，try-join 早取消、`JoinHandle::abort`、以任意顺序取消所有任务的 runtime shutdown，Dropwise 都没有强调 ([RFD 400](https://rfd.shared.oxide.computer/rfd/0400))。`select!` 两个分支在同一次 poll 中都就绪时谁赢，这是 GFuzz 探索的核心维度，GFuzz 在 7 个 Go 项目中找到 184 个新 bug ([GFuzz ASPLOS'22](https://par.nsf.gov/servlets/purl/10321048))；Tokio 的 `rng_seed` 能让这个顺序可复现，但需要 `tokio_unstable` ([tokio PR #4910](https://github.com/tokio-rs/tokio/pull/4910))。还有 SQLite 的 fail-continuously 模式 ([SQLite testing](https://sqlite.org/testing.html))：被重建的同一 target 在每次重试的第 k 个 Pending 都取消，用来暴露“每次取消泄漏一点”的累积型 bug。笔记还提到一个容易被忽略的 plan 优先级：第二次取消落在第一次取消触发的清理或重试路径上。Java 废弃 `Thread.stop` 的文档专门讲过“清理过程中又来一次中断” ([Oracle](https://docs.oracle.com/javase/8/docs/technotes/guides/concurrency/threadPrimitiveDeprecation.html))，Sethi 等也记录过 double-exception 跳过剩余清理的案例。

## 零配置接入：CancelSan 与复用现有测试

G0 显示，可行性的瓶颈在“能不能挂到现有测试上”：有 6 个案例卡在旧构建环境，很多站点是 combinator 或自定义 wrapper。这和 Fray 的结论一致，其作者强调“applicability”比搜索算法更重要 ([Fray](https://arxiv.org/pdf/2501.12618))。Rust 生态里已经有一一对应的接入机制。madsim 用 `package = "madsim-tokio"` 加 `--cfg madsim`，并声明正常构建时补丁 crate 与原版完全相同 ([madsim](https://github.com/madsim-rs/madsim))。Cargo 允许在 config 文件里写 `[patch]`，官方原话是这种写法“通常只适合由外部构建工具自动生成” ([Cargo config § patch](https://doc.rust-lang.org/cargo/reference/config.html))；补丁源的版本号必须满足依赖方的要求，同一 crate 的多个版本可以用 `package` 键分别打补丁 ([Overriding Dependencies](https://doc.rust-lang.org/cargo/reference/overriding-dependencies.html))。所以 `cargo dropwise test` 的最小形态是（推断）：读 `Cargo.lock` 拿到 tokio 的精确版本，从本地 registry 复制源码，应用对应 minor 版本的补丁（锚点是 `select!` 元组构造处和 `Timeout::poll`），生成临时 config 注入 `[patch]` 和 `--cfg dropwise`，再用独立的 target-dir 避免冲掉正常的构建缓存。整个过程不改用户的文件。RUSTFLAGS 变化会导致全量重编译，对大型项目的耗时**还没测过**。

复用现有测试之后，oracle 可以分层叠加，不需要用户写场景（推断）。第一层是测试自带的断言，前提是 baseline 稳定通过（NonDex 式差分）。第二层是挂起判定，超时阈值从 baseline 时长推导，参照 cargo-mutants 先跑一遍未修改的源码树来设定超时的做法 ([cargo-mutants baseline](https://mutants.rs/baseline.html))。第三层是静止后的 obligation 和孤儿任务检查。第四层可选：条件断言 `dropwise::was_cancelled_at(...)`。Filibuster 在 Netflix 示例中执行 1606 个测试，**只需要 9 条条件断言** ([Filibuster SoCC'21](https://rohan.padhye.org/files/filibuster-socc21.pdf))。注入的是规格允许的 Pending，而不是像 Filibuster 那样注入 503 错误，所以“测试按理就该在注入下失败”的情况应该更少。主要例外是“注入让 timeout 分支获胜，而测试断言请求成功”，这一类可以标为“可能是测试脆弱”（推断，需要在 G0 的 4 个 eligible 案例上验证）。

对 Dropwise 补丁覆盖不到的站点，有两条便宜的路。一是 knob 化：自定义 timeout 写成 `dropwise::knob(Duration::from_secs(30))`，测试时由 plan 返回 0、1 tick 或原值，借鉴自 FoundationDB 的 BUGGIFY ([BUGGIFY](https://transactional.blog/simulation/buggify))。二是 futures combinator 替身：futures-rs 全仓库没有一处 cancel safety 文档，而 RFD 400 把 `SinkExt::send` 和 `try_join*` 列为取消来源 ([futures-rs](https://github.com/rust-lang/futures-rs); [RFD 400](https://rfd.shared.oxide.computer/rfd/0400))，因此为 `futures::future::{select, try_join_all}`、`StreamExt::then` 提供同签名替身，是覆盖面增长最快的方向。madsim 不得不逐个 fork 周边 crate，这个负担说明“给每个 combinator 打补丁”难以持续。在 Tokio `coop::poll_proceed` 叶子层注入 Pending、从而与 combinator 无关，是笔记提出的替代方案，但目前**只是推断**。

## 把 Tokio 文档化的不安全 API 变成内置模型

研究者对 Tokio 主仓库（commit cdd9dae，2026-10-16）做了全量提取，`tokio/src` 下共有 119 处 `# Cancel safety` 小节。自写脚本粗分并人工更正 3 处误判后，结果是 73 处 cancel safe、17 处丢队位、24 处不安全、2 处保留部分进度。丢数据的有 `read_exact`、各定长 `read_u16…f64`、`read_line`、`write_all`、`mpsc::Sender::send`、`Barrier::wait`，以及 tokio-util 的 `Framed` 的 `SinkExt::send`。丢队位的有 Mutex、RwLock、Semaphore、Notify 的所有获取方法和 `reserve*`。部分进度型的有 `read_until`、`write_all_buf`、`flush` ([tokio-rs/tokio](https://github.com/tokio-rs/tokio); [tokio::select!](https://docs.rs/tokio/latest/tokio/macro.select.html))。由此可以做三件事（推断）：对 data-loss 类自动注册 obligation（例如 `Sender::send` 的值随取消被丢弃，这是 Tokio 文档自己承认的） ([mpsc Sender 文档镜像](https://mirror.whynothugo.nl/vdirsyncer/v2.0.0-beta0/tokio/sync/mpsc/struct.Sender.html))；对 fairness-only 类默认降级为警告，与 RFD 400 的“mostly cancel-safe”术语对齐；在报告里用“官方文档已标注不安全”来解释失败原因，但不作为判错依据。另外，`dropwise::conformance::recv_like(...)` 这类通用一致性套件，可以帮库作者动态验证自家 API 的 `# Cancel safety` 声明，形态参照 Trio 的 `check_one_way_stream` ([Trio testing](https://trio.readthedocs.io/en/stable/reference-testing.html))。

这一主题要压一压预期。笔记引用的 G0 分布是 22 个案例中 13 个为 `select!`/`timeout`，但其中真正属于 Tokio 文档化不安全 API 的只是一部分，多数 bug 是应用层“消费后、提交前”的窗口，例如 aselect README 里的 `receive_command` ([aselect](https://github.com/avl/aselect))。所以模型库应定位为“解释器 + 免费 oracle”，而不是主要检出手段（推断）。还有一个需要避开的坑：async-rust-lsp 的黑名单把 `read_buf`、`write_buf` 列为不安全，与 Tokio 官方文档相反，应以 Tokio 文档为准 ([async-rust-lsp](https://github.com/rgbkrk/async-rust-lsp))。另外几个可以直接加的模型：带投递计数的 `Sink`，用来判 exactly/at-least/at-most-once，思路来自 outbox 模式 ([microservices.io](https://microservices.io/patterns/data/transactional-outbox))；`guarden`/Dropshot 式“转交给 spawn”的 obligation 第三态，避免在 drop 当下误判 ([guarden](https://github.com/ZnqbuZ/guarden))；`taken(&mut slot)` 补偿 helper，在拿走状态的同一行创建 obligation，来自 Weimer & Necula 的补偿栈，该工作在近 400 万行 Java 中发现 800 多处错误处理缺陷 ([OOPSLA'04](https://people.eecs.berkeley.edu/~necula/Papers/rte_oopsla04.pdf))。

## futurelock：取消的反面，一个没人覆盖的 bug 类

Oxide RFD 609 定义的 futurelock 不是“drop 得太早”，而是“既没 drop 也没 poll”。任务先 poll 过 F2，使 F2 进入了锁的等待队列，随后转去 await F1，而 F1 需要 F2 持有或将要获得的资源。典型形态是 `select!` 中一个分支传 `&mut future1`（在等锁），另一个分支是 sleep；sleep 赢了之后，分支体内又去 await 同一把锁，公平 Mutex 却已经把锁交给了无人 poll 的 future1。真实事故 omicron#9259 导致所有用数据库的请求挂起，最后靠 DTrace 才定位。RFD 把“警告 `&mut future` 分支加分支体内 await”的 lint 列为开放问题 ([RFD 609](https://rfd.shared.oxide.computer/rfd/0609))。Dropwise 的 `select!` 补丁天然处在检测位置（推断）：补丁能识别分支是 `&mut` 引用。最简单的版本是 settle 超时时报告“存在被 select! 保留但 N ms 没被 poll 的 future”。配合静止判定的“死锁”态和 Tokio task dump（需要 `tokio_unstable` 加 `tokio_taskdump`，仅限 Linux）([tokio dump 测试](https://codebrowser.dev/tokio/tokio/tests/dump.rs.html))，可以把“超时”变成“卡在哪个 await”。工作量 M，属于“中垂果实”。

## 降成本与报告分诊

对重型 e2e 测试，“每个 plan 一个进程”撑不住。笔记给出的成本阶梯（推断）从便宜到贵依次是：baseline 探测运行，建立“测试 → 站点 → Pending 次数”索引；只对观察到 Pending、且不属于 arid 类（如 `ctrl_c()`、shutdown 分支、测试脚手架内的 select!）的站点生成 plan，参照 Google 突变测试对无覆盖和 arid 节点的过滤 ([Google mutation testing](https://research.google/pubs/state-of-mutation-testing-at-google/))；同一站点先在最便宜的测试上试，暴露即停（PIT 的做法）；轻量测试在宏内循环执行，加上 AFL 式 stability 检查；重型测试每次运行每个站点最多注入一次，种子随 CI 轮换，失败后用 NonDex 二分确认。快照、fork 和 CRIU 暂不考虑。Go `-race` 和 Uber 的落地经验支持“默认报告、不阻断”。Uber 离线周期运行，约 6 个月检测出约 2000 个 race，开启 race 后测试 P95 时长从约 25 分钟升到约 100 分钟，因此没有放在 PR gate 上 ([Uber Blog](https://www.uber.com/blog/dynamic-data-race-detection-in-go-code/))。效果签名归并能处理“同一个 await 在重试循环里 Pending 1000 次”这类情况：相邻 Pending 之间如果没有 obligation 创建或 resolve、也没有模型的出入队，就合并成一类，思路来自 DPOR、Legolas、FATE ([Legolas NSDI'24](https://www.usenix.org/system/files/nsdi24-wu-haoze.pdf); [FATE NSDI'11](https://usenix.org/legacy/events/nsdi11/tech/full_papers/Gunawi.pdf))。但 target 内部的缓冲可能在没有外部效果的情况下发生变化，所以这只是启发式，不是可靠的归约。

报告这一侧，成熟工具有三点共识：以站点或栈为键去重；每份报告附可直接执行的复现命令，并持久化失败用例、下次先重放（proptest 的 `proptest-regressions/` 保存的是种子而不是值）([proptest](https://proptest-rs.github.io/proptest/proptest/failure-persistence.html))；展示在开发者已经在看的地方。Boost.Test 的 `itest::exception_safety` 悄悄消亡，留下的教训是用户最想知道“失败是在哪里注入的” ([Boost 邮件](https://listarchives.boost.org/Archives/boost/2005/12/98095.php))。所以每个违例都应该打印注入点源码位置、Pending 序号和赢下的分支。另一个低成本的价值是覆盖报告：哪些站点被触达、哪些观察到 Pending、哪些真正被取消过、哪些清理探针从未执行。Yuan 等发现，错误处理代码做到 100% 语句覆盖就能暴露相当一部分灾难性失败 ([Yuan OSDI'14](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/yuan))。笔记据此推断，“告诉用户实际测到了什么”可能比 bug 检出更早被用户接受。评估口径上，Miri 用“能无改动跑起来的现有测试比例”（超过 70%）作为首要指标 ([Miri POPL'26](https://research.ralfj.de/papers/2026-popl-miri.pdf))。Dropwise 可以照此把 G0 中的 6 个 unknown 当作分母问题来看。

## 证据边界：未核验项与笔记之间的分歧

几项关键依赖**没有核实**，落地前需要先查。`RuntimeMetrics::num_alive_tasks` 从哪个 Tokio 版本起不需要 `tokio_unstable`，没有查 CHANGELOG；而 G0 涉及 1.17–1.53 的版本跨度，这会决定孤儿任务 oracle 能否用于老案例。Tokio 有没有查询 current_thread 空闲状态或下一个定时器时刻的公开 API，没有确认。PR #6113（关闭 auto-advance 的开关）是否合并，没有确认。paused time 下同一时刻到期的定时器顺序是否可控，没有查。在 coop 叶子层注入能否覆盖 combinator，是纯推断。“单次取消覆盖绝大多数取消 bug”没有文献，要用 22 个案例统计。“timeout 分支获胜下的失败多半是测试脆弱”这一分类，要在 4 个 eligible 案例上验证。RUSTFLAGS 导致全量重编译的代价没有实测。几处二手数字也要核对：Luo 等常被引用的“async wait 占 45%”、Yuan 等“58% 可由简单测试发现”和“90% ≤3 节点”、Tu 等 Go 研究的 58%/42%、TSVD 的 100ms near-miss 参数，以及 Async/Await 设计空间论文把 Rust 归为“unaware cancellation”的说法（只读到摘要页）。Chipmunk“系统调用内部崩溃点”的解读来自研究者已有的了解，不是全文。POSIX、Go context、crash-only software 的 URL 在笔记里标为“未本轮核验”。Strict linearizability 是否真能保证 limited effect，学界有争议 ([arXiv 2309.05230](https://arxiv.org/pdf/2309.05230))。

笔记之间**高度重叠**的地方，本身就是可信度信号：{pre, post} oracle 独立出现在三份笔记里（异常安全与崩溃一致性、调度与 Jepsen、oracle 专题）；孤儿任务 oracle 出现在四份里；静止判定出现在四份里。**分歧和数字出入**有以下几处。第一，goleak 的重试参数：一份笔记直接引用了 `options.go` 源码（20 次，1µs→100ms），另一份说在 README 和 pkg.go.dev 上没找到；以源码为准。第二，LFI 的恢复代码覆盖率提升，一处写“从几乎为零到 60%”，另一处写“35%–60%”。第三，Uber race 修复数在不同来源中分别是约 1000 和约 1100。第四，对“内层 await”的看法：崩溃一致性笔记认为 Rust 的 drop 自外向内，外层第 k 个 Pending 处 drop 已经覆盖了所有内部挂起点，差别只在报告；接入笔记则主张在叶子层注入 Pending 来覆盖 combinator。两者并不矛盾，前者讲“在哪里 drop”，后者讲“哪里能产生 Pending”。第五，成本策略：调度笔记主张 c=1 穷尽、c≥2 分层采样；接入笔记主张重型 harness 每次运行多站点各注入一次，再二分确认。这对应两种场景，可以用 `--exhaustive` 和 `--sample` 并存。第六，Antithesis sometimes assertion：一份笔记引用了官方文档，另一份说没取回原文。第七，Asupersync 自己承认 24 个 oracle 中有 13 个没接入，却在报告里记为通过，引用它的覆盖面时要谨慎 ([Asupersync](https://github.com/Dicklesworthstone/asupersync))。

## 建议的下一步：五个小实验

下面的顺序优先安排最便宜、最能决定后续投入方向的实验，都不需要先做完整功能。**实验一（约半天，纯案头）**：给 G0 的 22 个案例补四列，分别是需要的取消数 c、需要的 timing、bug 是否落在 Tokio 文档化的不安全 API 上、取消来源类型（select!/timeout/try_join/abort/combinator/自定义 wrapper）。这一步直接回答三个问题：模型库的上限有多高，c=1 默认值是否成立，“竞争者 = Err”和 abort 这类新 plan 维度能覆盖几个案例。**实验二（几天）**：在已有的配对对照（Notify lost-wakeup、io_uring fd 泄漏）和 4 个 eligible 案例上，手工写一个**只用通用状态**的 `observe()`（队列长度、计数器、槽位是否为 None），刻意不看修复内容，然后检查 {pre, post} 判定能不能在 bug 版本上报错、在修复版本上保持安静。这是对“条件是读过修复后才写的”这一弱点最直接的检验。可以顺手用 cargo-mutants 式变异（删掉 rollback 语句，把 `reserve` 加 `send` 改回 `send`）在修复版上造出盲 bug，测量 oracle 的检出率 ([cargo-mutants](https://mutants.rs/))。**实验三（一两天）**：先核实 `num_alive_tasks` 的版本门槛，再在同一批案例上比较取消运行与 baseline settle 后的存活任务数，看能否发现现有 obligation 漏掉的孤儿任务。**实验四（几天）**：在之前“立即观察在修复代码上误报”的案例上，比较三种观察策略：固定窗口、T 与 2T 敏感性自检、用 auto-advance 跳变加 `yield_now` 探针近似的静止判定。这样能量化静止判定值不值得做成 M 级功能。**实验五（几天）**：对 G0 中“现有测试没在站点上产生 Pending”的案例，以及能构建的 unknown 案例，先跑两遍 baseline 做确定性自检，再套上 `interleave_pending` 或 `duplex(1)` 式的 Pending 制造器，看 eligible 数能否从 4 往上涨。如果能涨，`cargo dropwise test` 这个 M 级工程才有足够多的案例来证明它的价值。

## Conclusion

这次调研改变的主要是投入方向的判断。Dropwise 在“搜索”这一维上已经站在 CHESS、SCTBench、Lincheck 的延长线上，再加搜索算法的边际收益不高。真正缺的是一个自动、不依赖 bug 知识的判定，以及一个有原则的观察时机。三个部件（baseline 派生的允许集合、静止判定、孤儿任务差分）恰好分散在异常安全、Go 和 Trio 测试工具、Go 泄漏检测三个互不往来的社区里，这就是“人类注意力盲区”在这里的具体形态。它们的组合还顺带解决了 Dropwise 评估方法上的一个硬伤：不变式不必再“读过修复才写得出来”。

第二个认识是，Dropwise 的第一价值可能不是“找到新 bug”，而是“讲清楚测到了什么”，包括覆盖了哪些站点和时序、哪些结论只能算 inconclusive、哪些失败来自对抗性时序。静态检测器 16 个候选 0 个确认，G0 只有 4 个 eligible，这说明在 Pending 能被触达、观察时机被理顺之前，用 bug 数衡量工具的成败为时过早。先用上面五个小实验把这两个前提量化出来，再决定 CancelSan 和 futurelock 这两项 M 级投入的顺序。
