# 从取消测试到进度见证与在线门控

> 2026-10-22。研究提案，承接 [交接边界理论](THEORY.md)。本文吸收两份 eBPF／OS-runtime 研究咨询中的可用方向，并按一手文献与实际接口收紧实现条件。在线门控已有研究原型，Rust 字段契约也已落地；自动规则提取、跨内核见证仍是提案。当前决策见下面的收尾更新，实验以各阶段 RESULTS 为准。

**值得推进的方向是：离线找出会伤及后继的中断窗口，提炼判断交接是否合法所需的最少状态，再把判断放到真正能阻止错误复用或错误清理的地方。** eBPF 可以提供缺失的内核事实，也可以帮助选择故障窗口，但不是这条路线的前提。

这比继续增加同类客户端更有机会带来方法增量：不仅发现一个错误，还回答为什么现有守卫漏掉它、最少增加什么信息能挡住它，以及这条规则能否迁移。近期以库内守卫和现有测试做出闭环；编译器与 OS 协作是后续可以认真探索的方向，不必先建设一个通用 runtime。

## 当前收尾判断：跨层责任中断与状态失步

2026-10-22，吸收最新研究评审和两条实现线的结果。**主攻离线跨层失步发现，在线守卫作为责任交接与修复机制的参考实现。** 这不是放弃在线问题，而是把主张放在最有实质支撑的地方：取消以后，词法作用域、客户端状态机和远端协议可能各自前进；错误不仅是泄漏，还包括后继假成功、合法工作被误清理，以及恢复读到了旧回复。

### 采纳的研究判断

- **区分安全许可与成本选择。** 业务契约决定能否补完或重试，责任关系决定谁能回滚或销毁，协议进度决定怎样恢复帧边界。权限与协议前提已经确定后，迟到响应与永久无响应的不可区分性主要形成等待／重连的成本问题，不能用故障标签当在线特征。
- **停止扩展本轮恢复策略学习，采用确定性有界恢复。** 保留修正后的学习实验作为负结果，不删除历史。优先局部撤销、在明确完成边界内排空／回滚、预算耗尽后淘汰；恢复阶段共用总预算。探测是获取新信息的动作，不是提前知道故障类型。当前 PostgreSQL 实验已经展示预算短会淘汰慢连接、预算长会增加等待，足以支持这个分层设计。
- **离线贡献不只在报出异常。** 目标效果、后继效果、客户端／服务端状态以及跨字段关系必须分别表达；校准缺失、退化和不稳定不能被整体观测掩盖。Rust 版本现已支持字段与关系，但它们仍由作者声明。发现增量、诊断增量和迁移成本分别衡量。
- **同步信号用于暴露非原子窗口，不承诺任意指令点透明恢复。** 自然 asyncio 取消、Rust future drop 与同步信号分别报告。在线强制点仍是显式操作及资源交接边界。

### 纠正评审中的事实与推导

1. **预注册构造期清理不是新发明。** `tokio-postgres` 的 `TransactionBuilder::start()` 已在发送 BEGIN 前创建 `RollbackIfNotDone`，明确处理事务对象尚未返回时的取消。本轮真实上游实验也验证了这个正面对照。研究增量应放在系统发现保护遗漏、跨层组合以及实际交接处的强制，而不是声称 RAII 必须假设异步获取原子完成。[源码](https://docs.rs/tokio-postgres/0.7.18/src/tokio_postgres/transaction_builder.rs.html)
2. **Go `SessionResetter` 并非只在归还池时触发。** 它在复用前运行；官方文档也明确包含未回池而直接复用的情况。归还前有效性检查是 `Validator`。不能用错误的调用时机制造差异。[官方接口](https://pkg.go.dev/database/sql/driver)
3. **关闭解决拒绝复用，不等于撤销效果。** 已提交的请求、已发送的数据和其他活跃使用者都需要单独处理；取消后“不再主动补发”不能改写成“远端绝不会生效”。重连耗时也不是无条件有上界。不可区分执行不产生“一半概率出错”的结论。
4. **Pipeline 不等于独立流的多路复用。** PostgreSQL 在连接上按序处理结果，并在错误后跳过命令直到同步边界；HTTP/2 一类有独立流身份的协议是另一种责任形态。都值得研究，但不能用同一个队列示意替代两者的契约。[PostgreSQL 文档](https://www.postgresql.org/docs/current/libpq-pipeline-mode.html)
5. **恢复预算比例不是现成定理。** 评审建议的 `0.2–0.5 × 重连耗时` 没有由给定模型推出；作为候选配置可以测量，不能标成 ski-rental 的解析最优解。当前先使用显式预算和敏感性对照，不增加学习器。

### 下一轮按机制推进，不按项目数量推进

优先两种形态：**池借出交付期间的取消**（资源／配额已转移但调用者没拿到 guard）和**管道中一项取消后的合法剩余责任**。前者检验跨任务交接，后者检验连接级淘汰的权限边界。先复用现有探索与成熟客户端，不预建通用责任树或多协议框架。

固定调用契约、预算和判定语义后，与普通定向取消测试、实际上游 reset／驱逐策略及整体判定器比较。整体判定器也应能表达相同的合法效果组合，不能人为限制成“仅全前态或全后态”来制造字段级优势；协议规范之外，API 对取消、事务和重试的公开承诺也是契约来源。跨实现迁移与跨协议迁移分开统计，适配所需源码阅读不是失败本身，关键是是否需要先知道 bug 才能写判定器。

- 找到独立责任遗漏且强基线漏掉：推进发现方法与机制分类。
- 发现集合相同但声明、校准或定位更好：明确主张方法效率和诊断质量。
- 成熟上游已有小而完整的保护：把它作为正面对照和修复模式，不再另造在线替代品。
- 只有真实场景证明单 owner／标量标记不够时，才增加权限结构。

已有小补丁和成熟先例不会使这条研究线失去价值；它们让比较更强，也让“发现—解释—修复”闭环更扎实。阶段结果见 [在线结果](../online/RESULTS.md)、[离线结果](../../prospective/offline-discovery/ROUND5-RESULTS.md) 和 [三个上游补丁](../../prospective/phase4-exploration/python/pg-mysql/upstream/README.md)。以下章节保留较早的机制探索；其中规则综合、eBPF 和编译器方向不覆盖上面的当前优先级。

## 1. 从残留状态转向责任与权限

Rust future drop、Python 协作式取消和内核错误返回不是同一种控制流机制，但都可以产生这样的窗口：执行体已经改变了其他状态域，完成、恢复或移交责任尚未结束，执行体却先退出。问题不在于中间状态本身，而在于后续是否仍按一个不成立的前提继续使用或清理它。

把观察拆成三项，不能用一个 Dirty 位替代全部语义：

| 观察对象 | 要问的问题 | 现有动机 |
|---|---|---|
| 目标效果 | 未发生、已发生、合法部分完成，还是结果未决？ | 远端可能已执行，取消本地等待不能撤销它 |
| 复用资格 | 这个连接、事务或流能否执行指定的下一操作？谁负责恢复？ | Skytable 的旧响应可能被 query 或池验证消费 |
| 清理权限 | 本对象实际取得过什么资源／引用，能释放哪一份？ | multicast 失败 socket 的关闭可能伤及另一个正常 socket |

后两项可以在不知道目标最终效果时仍作出有用决定。例如远端是否提交仍是未知，但本地可以拒绝把未同步连接交给下一请求。反过来，拒绝复用也不自动证明原操作违约，更不提供安全重试保证。

由此保留三个研究假设：

- **交接见证假设：** 对一类明确接口，少量带对象身份的进度与责任信息，足以阻止大部分后继污染，不需要复制完整业务状态。
- **信息增量假设：** 某些合法和非法执行在用户态现有观测下不可区分，内核事实或协议阶段能把它们分开。先找到这种执行对，再决定加哪种探针。
- **离线提取假设：** Dropwise 的反例和合法对照能帮助选择、简化门控规则，减少纯手写状态机遗漏；不是把每个已知补丁改名为自动综合。

这三个假设应分别检验。见证有用，不代表需要 eBPF；手写门控有效，也不代表离线提取已经有增量。

## 2. 在线机制先保护一个窄边界

第一版只保护独占使用的有状态连接及其 direct／pooled 入口。责任由协议库声明，守卫放在库的操作入口和池的验证／归还关口，不从 Tokio task ID 或 TCP 字节数猜测 SQL 事务。

一个候选状态机是：

```text
Reusable -> Active -> Reusable
                 \-> Quarantined -> Reusable | Retired
```

- `Reusable` 表示满足本接口的复用条件，不表示远端没有发生效果。
- `Active` 表示当前代操作有尚未结算的责任。守卫须在可能产生相关效果前建立，而不是等一次 write 成功后才置位；被 poll 的子操作可能先推进内部状态再返回 Pending。
- 中断后，有未决责任的对象先退出普通复用通道。`Quarantined` 期间由明确的恢复者独占，恢复成功才重新放行；没有已验证恢复路径则进入 `Retired`。
- 已完整结算后发生的尾随取消不应重新污染资源；协议已完成但事务仍打开时，也不能仅凭“读完一帧”清除事务责任。

这里的状态是候选设计，不是公共 API。简单独占协议可能只需一个未完成标记；事务与协议可以同时未决，多路复用还需要 stream／request 身份、代次和共享责任，不能预设统一的两位编码。

### 放行与恢复的约束

1. **检查和交接是同一受控过程。** 下一次业务调用、池验证及自动重试都必须经过关口，不能先拿旧回复做 PING 验证，再检查污染标记。独占句柄可复用现有所有权；跨线程版本需明确同步，不承诺无跨核成本。
2. **结算必须属于同一对象和同一代操作。** 老请求的迟到回复、老恢复者的完成事件，不能把新一代资源标为干净。责任转交后台时，要有接收者和完成条件；“已入队”不是“已完成”。
3. **隔离与物理回收分开。** 恢复队列须有容量、截止条件和 runtime 关闭策略；队列满、恢复再次被取消或状态缺失时不得默默放回池。重连限速与背压用于控制可用性损失，不能通过重新放行可疑对象来减轻压力。
4. **恢复动作来自协议，而非通用排空猜测。** 读到 WouldBlock 不证明远端不会再回复；PING 也不证明事务已结束。PostgreSQL 的 `DISCARD ALL` 不能在事务块中执行，不能当作未决事务的通用回滚替身。[PostgreSQL 文档](https://www.postgresql.org/docs/18/sql-discard.html)
5. **防护不是无代价的正确性。** 淘汰连接会丢失会话状态并影响在途工作；多路复用下可能伤及其他请求。必须声明隔离粒度及对外错误／结果未决语义，不自动重放业务操作。“局部、单调”是设计线索，不是安全性的充要条件。

对强制门控，权威状态应与使用权一起受控，异步日志只做诊断。探针缺失或事件丢失先标记观测不完整；如果策略选择拒绝复用，单列这类保守拒绝的成本，不能计作确认缺陷。仅观察模式可以停止告警，但不能据此声称仍提供防护保证。

## 3. eBPF 的三个具体用途

### 跨层事实与完成见证

先用现有代理、协议标记和可用的普通 socket 查询。只有它们无法区分关键执行时，才增加 eBPF：例如确认响应已经进入内核、某次读取已消费数据，或某项具体后台责任已完成。

TCP 未读字节数只是一个观测维度：合法通知可能使队列非空；旧响应进入用户态缓冲后，内核队列可以为空；远端尚未响应时也可以为空。因此 `rcv_nxt - copied_seq` 既不是通用违规条件，也不是通用放行条件。[PostgreSQL 异步消息](https://www.postgresql.org/docs/18/protocol-flow.html#PROTOCOL-ASYNC)

完成见证必须逐项定义。socket 析构不等于数据库事务结算；一次 CQE 不等于整个 runtime 静止。`synchronize_rcu()` 只等待宽限期，不保证所有排队回调执行完，不能用它或一个用户态屏障替代对象清理完成条件。[RCU 文档](https://docs.kernel.org/RCU/rcubarrier.html)

对象 cookie／代次、操作 ID 和协议身份比当前 PID/TID 更重要：网络处理可能发生在 softirq，后台清理由另一线程执行，多个 future 也可能共享一个线程。探针只证明它覆盖到的事件；跨 CPU 快照不天然原子，函数入口不代表函数内部的更新已经发生。

观测开销要用开／关探针对照测量，记录可实现切点是否改变。优先少量状态聚合；需要事件序列时再用 ring buffer 并处理丢失。不要把“不主动唤醒”当成没有观察扰动，也不预设固定纳秒开销。

### 按状态选择故障窗口

把“第 N 次分配失败”提升为“已确认某项状态发布之后，命中指定下游失败点”，有望提高有效注入比例并帮助跨目标迁移。条件必须对应真实状态更新后的可探测边界；宏、内联链表操作和任意函数中间位置不自动是 fentry 挂点。

复用内核现有 fail-nth／fail_function／failslab。仅在目标函数和测试内核确实允许时使用 `fmod_ret` 或 `bpf_override_return`，并匹配错误返回类型；返回 NULL 的分配器不能统一注入 `-ENOMEM`。eBPF 信号投递也不等于按指定指令取消 Rust future。[内核故障注入文档](https://docs.kernel.org/fault-injection/fault-injection.html)

### 生命周期被测对象

保留 `bpf_link` attach／失败清理和 sockmap 槽位替换为候选，先找真实的部分发布与责任移交，不因为对象名含 BPF 就纳入。Linux v6.12 的 `bpf_link_prime` 已预留 FD／ID／file，`settle` 安装预留 FD；不能虚构“最终 fd_install 分配失败”的切点。[源码](https://github.com/torvalds/linux/blob/v6.12/kernel/bpf/syscall.c)

Aya 可作为低成本源码筛选对象，但 0.13.1 的 `read_events` 在等待 readable 后同步读取，有事件或 lost 记录即返回，并非消费一批后 await 下一批。不存在的跨 Pending 半消费窗口不能靠增加运行次数补出来。[Aya 源码](https://docs.rs/crate/aya/0.13.1/source/src/maps/perf/async_perf_event_array.rs)

## 4. 内核侧优先检查清理权限

multicast 提供了不同于协议残留的机制：**失败对象的销毁会影响旁边的正常对象。** 下一步应把“复用失败对象”与“销毁失败对象后观察幸存对象”并列，而不只检查错误返回后是否泄漏。[已有收包与修复对照](../linux/RESULTS-round4-multicast.md)

候选见证要绑定具体 membership／group／设备／代次及成功取得的那份引用，不能用 socket 上一个“曾成功加组”的位代表全部成员关系。任务局部状态可用于跟踪一次调用；跨 syscall、worker 或 RCU 的责任须随对象转移。源码审查还要区分“调用过获取函数”和“确实获取成功”，以及返回成功是否承诺同步完成。

第一阶段仅做影子检查和现有补丁对照：合法清理必须消耗匹配的责任，失败路径不能凭未取得的责任释放他人的资源。接口允许的部分完成和异步接管应显式建模，不统一要求所有负返回都恢复 pre。

若将来在线阻断，必须由内核原生状态和受审查的清理路径提供权威见证；不能因 BPF map 查不到条目就跳过 decrement，那也可能是探针遗漏。Linux RV 已支持监控与反应，可借用其自动机与事件组织方式，而不是重做一套基础设施。[Linux RV](https://docs.kernel.org/trace/rv/runtime-verification.html)

## 5. 最小验证顺序

下面是后续实验建议，不改写已冻结实验计划。本轮只形成研究方向，不启动服务、内核探针或新实验。

### A. 从现有修复提炼可复用守卫

以 Skytable 的 query 修复对照为起点，保留 direct 和 pooled 两个关口。现有补丁已经提供“未完成交换使连接失效”的工程基线，不再把一个 Dirty 位算作新机制。首先问：更细的阶段信息能否在同样阻止串包的同时，避免不必要的淘汰？[补丁范围](../../prospective/phase4-exploration/clients/skytable/fix/README.md)

比较原版、现有保守作废补丁、阶段守卫，以及接口确实支持的恢复路径。另选一个已有正确取消处理的实现作负对照，而非假定主流池只检查 I/O Error；SQLx 的文档已经说明 acquire 中取消可能直接丢弃连接，事务对象也有 Drop 回滚行为。[Pool](https://docs.rs/sqlx/0.9.0/sqlx/struct.Pool.html#method.acquire)、[Transaction](https://docs.rs/sqlx/0.9.0/sqlx/struct.Transaction.html)

必要场景：无相关效果前取消、部分协议推进、内核为空但用户态仍有残留、正常结算后的尾随取消、合法后台接管、恢复失败／再次取消。事务单独验证会话责任；多路复用先作为适用范围反例，不强行套单连接位。

同时记录后继返回值与独立效果、不安全放行、保守拒绝、恢复失败、重连次数、尾延迟和吞吐；不要用“全部关连接”换来零污染而忽略可用性。已知坏版／修复版用于校准，迁移目标用于检验规则是否通用。

### B. 用同一场景测量跨层信息增量

在 A 中选择现有观测不能区分的执行对，对比仅用户态、普通 socket 查询、追加 eBPF 观测。覆盖“合法非空”“有害非空”“有害但内核为空”“远端仍在执行”和正确恢复。业务判定保持不变，新增观测只帮助区分状态与归因。

增量可以是新发现、确认实际覆盖、缩短等待或减少分析时间，不必每项都找新 bug。若已有观测足够，删除该探针；若同一观测仍对应不同合法性，明确需要增加哪项协议信息，不调阈值把样本硬分开。

### C. 用 multicast 检验发布与清理见证

沿用现有故障注入、收包和原版／修复对照，先记录实际阶段，不重造 runner。比较 ordinal 注入与可实现的状态条件注入，关注有效命中数／尝试数、接入成本和同预算发现，而非预设数量级加速。加入失败对象 close 前后的正常 observer；再选择一条经源码筛选的不同生命周期路径验证迁移。

### D. 由反例逐步细化在线规则（候选，当前不扩展学习器）

可以争取的方法贡献是识别缺少的事实，而不是学习等待时长。先由人声明资源、允许结果和可用恢复动作，再从小型候选规则中选择：操作未完成位、协议阶段、事务责任、对象代次、已接管责任。用 Dropwise 提供反例、合法取消和修复对照；遇到“同一规则状态，却需要相反放行决定”的执行对时，增加能区分它们的事实，而不是扩大拒绝范围掩盖缺口。

形成规则后，在未用于规则选择的输入、取消时机和第二目标上检验；与手写最佳实践、现有修复和简单作废策略比较，计入标注与接入成本。若删去离线探索后规则和结果完全相同，就把成果定位为实用守卫；若能更少标注地发现遗漏阶段或减少误拒绝，再推进规则提取／综合。

现有 `Obligation` 是测试期显式责任账本，不是在线强制机制，也不会从轨迹自动提取这些规则。先在场景侧验证规则，再决定是否值得增加核心接口。[实现](../../src/obligation.rs)

## 6. 长期方向

**编译器辅助的责任状态。** 让显式阶段注解与 async 状态机协作，生成取消时的隔离或责任转移代码，有望减少手写守卫遗漏。先用普通 RAII／类型状态原型检验表达力，再考虑 MIR。Rust 已有条件析构和 drop flags；同一个 await 在不同循环次数、分支和子 future 进度下可能带着不同责任，判别式不等于外部副作用账本，不能承诺零额外指令。[rustc 文档](https://rustc-dev-guide.rust-lang.org/mir/drop-elaboration.html)

**跨 runtime／内核的进度凭证。** 以 io_uring 一类异步所有权交接为候选，把操作身份、缓冲区代次、取消请求、原请求完成和回收权联系起来。先复用 SQE/CQE 和现有运行时所有权表，找到它们表达不了的契约后才讨论新增 ABI。取消请求完成与目标请求完成不可混淆；尤其返回 EALREADY 时仍需等待目标完成。[liburing 文档](https://github.com/axboe/liburing/blob/master/man/io_uring_prep_cancel.3)

**有界时间的逻辑作废。** 对硬实时，可研究先隔离旧代资源、再延后回收，但必须解决持锁、并发读者、设备访问和有界资源耗尽。O(1) 标记不等于可证明的最坏延迟，更不能据此宣称可在任意指令强杀线程。这是独立的后续问题，不是服务器门控原型的现成保证。

## 7. 如何判断这条路线值得继续

最有分量的结果不是“加了 eBPF”或“取消后不再出错”，而是：**找到了朴素作废策略或手写恢复遗漏的责任边界，用更少且可解释的状态把它保护起来，并在另一目标上复现收益。**

完整链条是：允许契约 → 有害与合法执行 → 所需见证 → 复用／清理关口 → 反例与迁移验证。检测能力、门控效果、离线提取收益和成本分别报告。若最后只有一个小而可靠的库修复，也应提交和复用；不为了研究叙事扩成并存框架。

相关理论与成熟实现见 [RELATED.md 的跨域部分](../RELATED.md#跨域责任与在线门控)。它们提供机制和对照，不替我们证明新颖性；也不能因为已有 poisoning、补偿栈或运行时验证，就提前否定这条组合路线。
