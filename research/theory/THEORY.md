# 交接边界上的取消正确性：Dropwise 的理论草稿

> 2026-10-21 整理。依据：[RESCAN.md](../../prospective/RESCAN.md)、[phase3/RESULTS.md](../../prospective/phase3/RESULTS.md)、[phase4-exploration/RESULTS.md](../../prospective/phase4-exploration/RESULTS.md)、[neo4rs/RESULTS.md](../../prospective/neo4rs/RESULTS.md)、[mechanisms/RESULTS.md](../mechanisms/RESULTS.md)，以及 [FOLLOWUP.md](../literature/FOLLOWUP.md) 中已核实的讨论。“已核实”表示读过原文或权威二手来源；其余标为待核实。
>
> 这是一份工作理论，不是“所有取消都能归约为原子操作”的定理。它给出一个可复用的提问方式：取消之后，谁接手资源、看到了什么、凭什么判断可以继续使用。

## 1. 模型

三样东西：

- **执行体：** 短命的控制流，例如 Rust 的 future、一次系统调用、一次带超时的 RPC。它“记得”一个多步操作接下来还要做什么。
- **共享资源：** 跨越多次操作存活的状态载体，例如 TCP 连接加远端会话、内核里的 `struct file` 和 socket、远端服务的状态。
- **交接边界：** 资源的使用权发生转移，或者同一个持有者开始下一次使用的时刻。例如连接还回池中、系统调用返回后另一个进程使用同一个 fd、ring 槽位被复用。

一个多步操作 P = p1; …; pm 执行到第 k 步时，正确性由执行体和资源**共同**维持：资源处于中间状态，执行体知道还要把剩下的步骤做完。取消（打断）抹掉了执行体，却把处于中间状态的资源留了下来；如果交接边界不做处理，这个中间状态就被交给了下一个使用者。

资源不一定在两个使用者之间转手。池化是“交给下一位借用者”；直接句柄是同一个持有者连续使用同一个 Client/Session/Conn。后者的交接边界不在借用/归还，而在上一次操作放弃使用权、下一次操作开始之间。

| 形态 | 交接边界 | 谁做复用决定 | 典型风险 |
|---|---|---|---|
| 池化 | 归还与下次借出之间，通常还包含验证/回收 | 池或 manager | 验证读到残留回复，脏连接被当成健康连接放回池中 |
| 直接句柄 | 同一持有者的两次操作之间 | 库的下一次调用入口，或契约明确要求的调用方恢复 | 旧回复留在流里，下一次调用未检查未完成状态，或恢复责任不明确 |

两种形态的共同点是：被取消的执行体不再拥有资源，但资源还带着它留下的中间状态。区别在于有没有一个独立的“复用关口”，以及这个关口能不能读到“交换未完成”的信号。池化把决定集中到 `is_valid`/`recycle`/`has_broken` 这类地方；直接句柄也可以在库的下一次调用入口检查、恢复或拒绝使用；若要求调用方先恢复，公开契约应说明这一责任。

## 2. 正确性条件：交接时允许什么结果

**锚点（已核实）：** Herlihy & Wing 1990（TOPLAS）在定义可线性化时处理了未决调用（只有调用、没有返回的操作）：“extending H to H' captures the notion that some pending invocations may have taken effect even though their responses have not yet been returned to the caller … Restricting attention to complete(H') captures the notion that the remaining pending invocations have not yet had an effect.”

**推广到交接边界：** 在交接之后的任何使用者和独立观察者看来，被放弃的操作必须属于调用上下文声明的**允许集合**。最常见的允许集合是“完整生效或完全没发生”，但它不是唯一一种：

- **全有或全无（atomic）：** 事务开始/提交、消息投递/确认、连接从边界状态开始下一次交换。调用方可以放弃时，允许 `pre` 或 `post`。
- **前缀（prefix）：** `write_all`、流式写入可能在写出一段前缀后被取消；契约允许“写了前 k 个字节”。这时“半完成”不一定是违规。
- **子集/混合（subset/mixture）：** 一次操作包含多个可独立生效的效果；每个效果可以各自选择“发生/没发生”，而不是要求整体同进同退。

**恢复后的比较（独立于上述效果契约）：** 执行显式恢复动作（drain、reset、reconnect、重试 SELECT、丢弃重建）后，按声明的观察范围比较后继操作与干净基线。本文把这种观察要求简称“恢复等价”；它可以与原子、前缀或子集契约组合，不是第四种目标效果分类。恢复动作本身成功，不代表元数据、协议关联和共享状态都恢复了。

“完全生效或完全没发生”只是第一种契约。具体采用哪种契约，要看所测操作的承诺和观察范围，不能仅凭“事务”“消息投递”等操作名称决定。目标允许部分进度，与后继返回值、邮箱元数据是否正确，应分别检查。

Dropwise 的判定是这个条件在“全有或全无”契约下的可执行版本：

- “没发生”和“已完成”不是手写的期望值，而是把同一个场景跑两遍校准得到的（`Verdict::Pre` / `Verdict::Post`）；
- 多个操作被放弃时，对每种组合做校准（`Verdict::Mixed`）；
- 两次校准不一致时记为无法判定（`Verdict::Unknown`），不算违反；
- 调用方的契约决定允许哪些结果：`Expect::Atomic` 允许任一，`Completed` 只允许已完成，`Undone` 只允许没发生（结果必须交到调用方手里的操作）。

这套判定只比较**场景实际返回的观察值**。它不证明没有被观察的共享状态没有变化，也不自动覆盖前缀、子集或恢复等价。前缀/子集目前要在场景不变式中显式检查允许条件（如内容确实为输入前缀）；只返回“已写入的字节数+内容”仍会按端点相等比较，并不会自动接受中间进度，不是 `Expect` 的现成取值；恢复等价则要先声明恢复动作和要检查的层。把这些说成“已经支持任意部分完成”会高估现有 API。

**和相邻概念的区别：**

| 概念 | 区别 |
|---|---|
| 可线性化 | 原定义针对并发对象和并发历史；这里是“资源被轮流借用”时，被放弃的操作对**继任者**的效果 |
| 异常安全的强保证（Abrahams） | 异常从下往上传播，每一层都知道自己因错误退出，可以清理；取消是从外部截断，而 Rust 的 `Drop` 是同步的，无法异步补偿 |
| 崩溃一致性 | 崩溃时执行体和内存一起死，重启后有统一的恢复流程；取消时只有执行体死了，内核缓冲区和远端会话都还活着，没有任何恢复流程被触发 |
| 数据库事务回滚 | 只保护存储层的数据，不保护连接上的字节流分帧和会话状态同步 |
| 隔离性 | 防的是同时发生的旁观者；这里防的是前任死后合法接手资源的**继任者** |
| strict linearizability（Aguilera & Frølund 2003） | 要求崩溃进程的未决操作在崩溃前生效或永不生效。放到网络 I/O 上做不到：请求可能已经在服务端执行，客户端在 drop 那一刻无法阻止它生效。所以我们把判定点放在交接边界，而不是丢弃的时刻 |
| durable linearizability（Izraelevitz 等 2016） | 全系统崩溃，易失状态全部丢失，然后统一恢复；我们这里是只有执行体死了，易失状态（缓冲区、会话）全部留了下来 |
| 可检测性（detectable recoverability，Friedman 等 2018；recoverable linearizability，Berryhill 等） | 由原来的调用者在恢复后判断“我的操作生效了没有”；这里提问的是交接边界上的守门人（池或调用方），要区分的是“静止（生效或没生效都行）”还是“半截”，而且判断出半截时可以直接销毁资源 |

（后三行的出处细节未逐篇核对原文，见 [FOLLOWUP.md](../literature/FOLLOWUP.md) 第八至十轮。）

### 恢复不是一件事

“操作又能用了”至少可能指四件不同的事：

1. **传输/连接可用：** 字节流没有错位，连接没有被对端或客户端关闭。
2. **业务操作序列可用：** 下一次请求拿到了自己的回复，事务/会话没有卡在前一个状态。
3. **API 元数据/协议关联准确：** 响应属于正确的请求，邮箱 flags、流的分片、请求号等没有和陈旧数据合并。
4. **共享/服务端状态一致：** 事务已提交或回滚，锁已释放，消息已投递或撤回。

这四个方面不是自动升级的层次；恢复了一个不等于恢复了另一个。IMAP 的 retry SELECT 是典型例子：重试后 APPEND/SEARCH/FETCH 都能完成（第 2 层），但 `Mailbox.flags` 和 `permanent_flags` 仍被上一次 SELECT 的 untagged 数据污染（第 3 层）。neo4rs 的例子更窄：幸存者的写成功、独立观察者也看到了，但紧接着同池的读静默丢掉自己的行；这是协议关联/后继正确性问题，不是“连接不可用”。SQLx 的问题则落在第 4 层：连接还能用，但事务状态留在了服务端。

直接句柄还有一个额外问题：没有池的回收关口，库也不一定在公开文档里说明 drop 后必须 drain/reset。BOLT direct 的例子是，切点后显式 `reset()` 能恢复操作，但公开文档没有说这是调用方的义务；所以只能记为未文档化的契约缺口，不能因为 reset 存在就说“调用方全责”。

## 3. 满足条件的三条路

1. **把资源带回边界状态：** 把交换做完，或者回滚。这需要一个仍能执行异步操作的清理上下文，比如 tokio-postgres 把 ROLLBACK 排进有序通道，或者后台清洗队列加硬超时，加上协议自带的 reset 命令。
2. **销毁资源并重建：** 一旦被打断就作废。Rust 的所有权是仿射的（值可以随时丢弃），而协议会话是线性的（必须走完）；`Drop` 又是同步的。所以第一条路常常走不通，实际可行的默认做法是第二条。
3. **把“未完成”状态传给做复用决定的一方：** 不要求当场把资源修好，而是让池、manager 或调用方明确看到“这次交换没有完整结束”，由它选择恢复还是销毁。bb8 在验证前标 `Invalid`、lettre 的 `sending`、sqlx 在 BEGIN 前增加事务深度，都是这条路。它不修资源，但改变了默认值：不能证明干净，就不放行。

第 3 条不是第 1、2 条的替代品，而是接口层的修复。很多问题真正缺的不是“再写一个清理函数”，而是让清理/复用决定拿到一个可靠的信号。

AsyncDrop 也不是银弹：清理本身可能在坏网络上卡住，隐式的中间状态没有守卫对象来触发它，`mem::forget` 和运行时关闭仍是逃生口。

## 4. 缺陷的形状：信号与决策之间的缺口

把已确认的问题放在一起看，几乎都是同一个形状：**“交换没做完”的信号已经存在，但做复用决定的地方没有读到它。** 直接句柄是同一形状的变体：信号可能存在（例如 mysql_async 的 `disconnected`），但下一次库调用未检查它；库可以在入口保护复用，或由明确的公开契约要求调用方恢复。

| 形态 | 实例（上游报告） |
|---|---|
| 信号和决策之间没有通道 | diesel-async 的连接池不读 mysql_async 的 `disconnected` 标记（diesel_async#304） |
| 取消路径上不发信号 | lettre 只在命令出错时标记连接（lettre#1170）；bb8-memcached 只在自身超时时标记（bb8-memcached#16） |
| 信号就在本层，却不检查 | mysql_async 直接持有的 `Conn`，被丢弃的命令留下了标记，后续命令照样执行（mysql_async#412） |
| 信号还没稳定就做决定 | bb8 在验证期间把连接放回池中（bb8#324） |
| 检查本身被残留骗过 | bb8 的验证读到残留的 `PONG`；deadpool-memcached 的回收检查太宽松（RESCAN 5.2，未上报）；neo4rs 0.8.0 的 `recycle` 只发一个 RESET、接受第一条 SUCCESS，被取消交换留下的 SUCCESS 被当成 RESET 的确认，后继者的读静默地少读了自己的行（[neo4rs/RESULTS.md](../../prospective/neo4rs/RESULTS.md)；上游已有 neo4rs#295/#298，修复只在未发布的 main） |
| 中间响应被当成最终成功 | async-smtp：取消后第二次 `send` 读到 DATA 的 `354` 并返回成功，消息实际已投递；第三封仍返回 `354`，不自愈（[phase4-exploration/RESULTS.md](../../prospective/phase4-exploration/RESULTS.md) §2；未冻结探索） |
| 会话状态在往返之后才提交 | sqlx-mysql 在 BEGIN 往返完成后才增加事务深度（sqlx#4467，与 Postgres 的 #4393 同一模式） |
| 恢复动作只覆盖一层 | IMAP 的 retry SELECT 恢复了 APPEND/SEARCH/FETCH，但 `Mailbox.flags`/`permanent_flags` 仍被陈旧 untagged 数据污染（[phase4-exploration/RESULTS.md](../../prospective/phase4-exploration/RESULTS.md) §3） |
| 直接句柄没有独立关口 | BOLT direct：切点后显式 reset 能恢复操作，但公开文档没有说明 drop future 后的义务；记为未文档化契约缺口，不是已确认的库缺陷（phase4-exploration §4.6） |
| 同一个信号，一条路径检查、另一条不检查 | Linux `epoll_ctl`：ADD 检查 `ep_create_wakeup_source()` 的失败并回滚，MOD 忽略它，返回 0，但 EPOLLWAKEUP 实际没有生效（[research/linux/RESULTS-round2.md](../linux/RESULTS-round2.md) 第 3 节；v6.19 和 v7.3-rc2 上实际复现，v7.3-rc6 的源码相同） |

**为什么有的系统天然安全：** 交接只发生在资源的静止状态，或者交接时销毁资源。具体有三种做法：

- 执行体和资源命运共享：崩溃时一起死，重启后统一恢复；
- 资源由一个总会把交换做完的后台任务独占：hyper 的连接任务（phase3 中 hyper-util、reqwest 零发现）、tokio-postgres 的连接任务。这只保证字节流不会错位；事务这类会话状态仍要显式处理，tokio-postgres 为此另写了一个 guard（RollbackIfNotDone）；
- 执行体被丢弃时资源跟着关闭：awc（phase3 零发现；“丢弃时关闭连接”来自执行者阅读源码的结论，未独立核实）。

**两层表述：** 第 2 节的条件是对外的正确性条件（跨交接边界的取消正确性）；对内的实现契约是**交接边界上的未完成状态可检测性**：资源是否处于可复用状态，必须能被做复用决定的一方读到，并且以此作为放行前提，否则重置或销毁。这里的“可复用状态”不一定是静止：交换未完成的显式标记也是可读信号。上表的每一行都是这条契约在某处断开了：信号没产生、没传过去，或者没被读。协议本身常常已经提供了信号，例如 PostgreSQL 的 `ReadyForQuery` 带一个事务状态字节（`I` 空闲、`T` 事务中、`E` 失败的事务中），问题在于通用池没有去读。配对扫描（[candidate-scan/PAIRING.md](../../prospective/candidate-scan/PAIRING.md)）检查的正是“做决定的一方有没有读到这个信号”，可以看作这条契约的静态版本，neo4rs 就是它找到、动态验证确认的。

**同构：** Rust `std::sync::Mutex` 的中毒机制。持锁时 panic 会让锁中毒，后来者必须显式处理；“取消时给连接打标记、池回收时检查”是同一个设计。

**设计原则：** 复用决定必须以资源状态可见为前提；不能证明可复用，就默认销毁或显式恢复，不要把“看起来可用”当成静止。**修复原则：** 把下层已有的“未完成”信号接到做复用决定的地方，并且在交换开始前就置位，完整结束才清除；如果一次恢复只能修好一层，要明确其余层由谁负责、怎么观察。

**为什么静态扫描找不到它：** 信号的产生方和决策方常常在两个 crate 里，单看哪一边都没有明显错误（candidate-scan 的结果）。

## 5. 测试方法（跨领域通用的部分）

把上面的案例压成七条当前认识：

1. **目标选择。** 事务建立、会话切换、checkout/验证、DATA/APPEND 这类边界，比普通请求的取消点更容易暴露问题（sqlx、bb8/BOLT、IMAP、SMTP）。
2. **观察后继。** 只看取消本身或后继 `Ok` 会漏掉旧结果、错误响应和未实际完成的效果（mysql_async、neo4rs、SMTP）。
3. **对象关联。** 同对象和异对象的后继暴露不同问题：前者看冲突/残留，后者看池/全局污染，不能互相代替（MongoDB MG1、neo4rs）。
4. **恢复分层。** 业务操作重新可用，不等于 API 元数据、协议关联和共享状态恢复（IMAP、neo4rs、sqlx）。
5. **结果与效果。** 具体返回值和独立观察要互补；两者一致才叫“后继正确”（mysql_async、sqlx、SMTP）。
6. **观察时间。** 立即复用看残留，完成信号后看清理；暂态不是泄漏（io_uring、Notify、neo4rs residue）。
7. **复用决策。** 未完成状态必须传到决定继续/恢复/销毁的一方；直接句柄没有池的关口，需要检查库的下一次调用入口和调用方契约（bb8、lettre、mysql_async、BOLT direct）。

| 部分 | 要求 | 是否通用 |
|---|---|---|
| 选打断点 | 优先建立会话状态的一次往返、checkout/验证、有副作用且回复晚于效果的调用、直接句柄的连续使用；普通只读请求收益较低 | 原则通用；具体机制按领域实现 |
| 选后继 | 同对象/不同对象、同操作/不同操作、原地重试/显式恢复后继续，按要回答的问题选，不要求跑满 | 原则通用 |
| 独立观察者 | 绕过被测资源确认实际效果 | 按领域实现 |
| 分开观察 | 目标进度、后继正确性、资源状态分别有字段，不能压成一个 `Ok` | 判定通用；前缀/子集需场景表达 |
| 判定 | 第 2 节的允许集合，两条基线由系统自己校准；多 cut 用 mixed，不稳定用 unknown | 对已声明契约通用 |
| 身份/关联 | 返回值要能对上请求、对象和操作；动态值先做符号归一化，不要直接删掉 | 原则通用；规范化按领域 |
| 观察时间 | 立即复用看残留，完成信号后再看清理；`Settle` 是观察窗口，不是完成证明 | 原则通用；静止判定未实现 |
| 初筛 | 交接时管道是否静止（残留字节、队列长度），以及有没有报错或卡住 | 原则通用；它看不到服务端还在计算的回复，只能补充、不能替代 |

**证据：** 回溯的消融阶梯（[RESCAN 6.7](../../prospective/RESCAN.md)）和前瞻实验（phase3）方向一致。会报错或卡住的问题，“取消后重试 / 换个操作看是否 `Ok`”就能抓到；静默的错误结果只有幸存者加独立观察者加两条基线才能抓到。phase4 exploration 又补了两个方向：SMTP 的 `Ok(354)` 是“效果已发生、返回值错”，IMAP 的 retry SELECT 是“操作可用、元数据不干净”。它们都不是单纯靠 `Ok` 或单纯靠残留字节能看见的。

**案例各自贡献了什么：**

| 案例 | 贡献的认识 | 不要从中读出什么 |
|---|---|---|
| sqlx `Pool::begin`（#4393） | 目标选择：建立事务的往返比普通查询更值；`Ok` 和独立连接看到的效果要分开 | 不是“所有查询取消都一样有价值”；T3 的零发现同时来自目标选择（没取消 BEGIN）和观察方式（回显） |
| bb8/BOLT `is_valid`（#324） | 复用关口本身是取消边界；状态要在验证前置位，否则旧回复会冒充验证 | 0/60、22/60 是计划执行计数，不是 22 个 bug；BOLT 是适配器证据 |
| mysql_async direct `Conn`（#412） | 直接句柄没有池的关口；信号在本地但后续库命令未检查，后继拿到旧结果 | 池路径干净，不能外推到直接句柄；一个根因 |
| MongoDB MG1 | 同对象/异对象后继暴露不同问题；M1 不是 B2 的超集 | 契约外行为，不计入确认问题；不能外推到所有事务 |
| async-smtp | `Ok(354)` 可以是“效果已发生、返回值错”；复用不会自愈，新连接才恢复 | 未冻结探索、未获上游确认；不是 24 个独立 bug |
| async-imap | 恢复分层：操作可用不等于元数据/协议关联恢复 | 一个根因；PR #150 只修 continuation 处理，不声称解决元数据污染 |
| io_uring | 立即观察与延迟清理要分开；暂态 fd 增加不是泄漏 | 机制对照，不是新 bug；有限样本 |

**成本：** 判定很便宜，成本在搭环境和写观察者上。phase3 中 AI 执行者为每个目标搭好四级场景用了 20–50 分钟。正因为判定不需要手写期望值，场景可以交给 AI 来写；但分诊仍要人来做：phase3 里 AI 把 mongodb MG1 判为确认的问题，复核时才发现驱动文档明确不保证这种用法，改判为契约外行为。

**证据边界：** 这些案例是存在性证据，说明某类问题真实、某类观察能看到它；它们不是检出率估计。phase3 的 8 个目标只确认 1 个问题，phase4 exploration 只覆盖 3 个客户端家族，而且是不冻结的首次接触。零发现只说明“在所列版本、场景和已实现取消点上没有观察到违反”。

## 6. 跨领域的同构（讨论部分的论据）

|---|---|---|

## 7. Linux 内核中的对应

| 概念 | 对应 |
|---|---|
| 执行体 | 一次系统调用、一个 io_uring 请求 |
| 共享资源 | 通过 fork 或 `SCM_RIGHTS` 共享的 fd、socket、pipe、文件偏移，io_uring 的环和缓冲区 |
| 交接边界 | 系统调用返回后，另一个进程或线程使用同一个对象 |
| 打断方式 | fail-nth 故障注入（`/proc/<pid>/fail-nth`、`/proc/self/task/<tid>/fail-nth`，已核实）、信号打断可中断的等待、进程中途被杀、io_uring 取消 |

**比 Rust 更好判定的一点：** future 被丢弃时调用方拿不到任何结果，系统调用被打断时调用方会拿到返回值。所以判定可以按返回值分情况：

- 返回错误码 ⇒ 效果应等于“没发生”（默认契约，有已知例外：例如 `close` 返回错误时 fd 也已经关闭，需要逐个系统调用确认）；
- 返回成功 ⇒ 应等于“已完成”；
- 返回部分完成（如短写）⇒ 按接口语义只允许那一部分生效。

**现有工作和空白：** syzkaller 用 fail-nth 做逐点注入，但判定靠崩溃类信号（KASAN、lockdep 等）；FIFUZZ（USENIX Security 2020）系统地对错误处理代码注入故障，但测的是用户态程序，判定只靠崩溃和 ASan（已核实）。“返回了错误码、没有崩溃，但共享对象被改了一半”这类问题，看起来是空白；未做全面检索。

**最小原型（不改内核）：**

1. 在打开故障注入的虚拟机内核里运行；
2. 用户态程序建好共享对象（socketpair、pipe、tmpfs 文件）；
3. 进程 A 执行系统调用，fail-nth 从 N=1 逐个注入；进程 B 在同一对象上做幸存者操作；
4. 用读写、`fstat`、`FIONREAD`、`/proc/self/fdinfo` 观察状态；
5. 两条基线各跑两遍，不一致记为无法判定。

信号打断放到第二步。风险：很多系统调用允许部分完成，需要逐个写清语义；部分内部状态在用户态不可见；先测哪个子系统要靠原型的结果来定。

**判定补充：** 返回错误码之后，如果后继者立刻收到明确的致命错误（内核主动把对象标坏），也算合法（`OK_POISONED`），相当于池丢弃坏连接。

**原型结果（[research/linux/](../linux/)）：**

- 第一轮：只用 fail-nth，6 个系统调用、105 次注入，0 违反。可行性得到证明，但 fail-nth 只能制造内存分配失败。
- 第二轮：加了信号打断和 fail_function（后者机制可用，但没有命中目标），共 14 个目标、1013 次注入，0 次无法判定。确认一个问题：上面第 4 节表中的 `epoll_ctl(MOD)`，在 v6.19 和 v7.3-rc2 上都能稳定复现，影响很小，不涉及安全。kTLS、overlayfs copy-up、POSIX 消息队列、被信号打断的 pipe 都是干净的。
- 契约外的例子：`connect` 被信号打断后返回 EINTR，连接仍在后台建立，这是 man page 写明的行为。
