# Phase 3 — Dropwise 确认结果

## 结论边界

Q2 盲判的 16 个真实风险候选全部进入 Q3。确认夹具的 **16 个 Dropwise 场景均为 `modelled`**，且均通过：无取消基线干净，注入首个 `Pending` 边界取消后，模型的外部不变量被违反。它们只证明 Dropwise 能复现所表达的机制，不证明目标应用当前代码确实发生该违反。

Neon SCRAM 候选另有一次隔离源码执行：Dropwise 直接编译并调用 Neon 固定快照中的真实 `ScramSha256::update`，在真实 PBKDF2 yield 点取消后，对同一对象重试得到 `invalid SCRAM state`。这项额外测试不是上述 16 个已提交模型之一；它不是 Neon 整个应用/代理路径的集成测试，也没有与某个修复前父提交作对照。依冻结计划，**没有一个候选达到“新缺陷候选”标准；本阶段新缺陷候选为 0**。未开 issue、未评论、未向外发布。

## 隔离源码执行：Neon SCRAM

从 `/tmp/dropwise-phase3-targets/neon` 固定 checkout 直接以 `#[path]` 编译该 commit 的 `sasl.rs`，临时 Dropwise crate 只提供 Rust crate 依赖，不复制或改写该源文件。使用其锁文件所解出的 `base64 0.22.1`、`hmac 0.12.1`、`rand 0.9.1`、`sha2 0.10.8`、`stringprep 0.1.2`、`tokio 1.43.1`。测试取真实 client nonce，提供合法 server-first challenge（salt=`c2FsdA==`，迭代数 2048），Dropwise 在真实 `hi` 的首个 `yield_now().await` Pending 点丢弃 `update`。之后真实 `update` 对同一 SCRAM 状态返回 `invalid SCRAM state`。包含该临时检查的 crate 测试共 3/3 通过，其中另外两项是源文件自身的测试。

这一证据比模型强，但范围仍是单个真实协议模块的隔离执行：没有构建 `postgres-protocol2` workspace crate、Neon proxy 或 PostgreSQL 端到端认证，也没有对照 fix parent。故只记 `isolated source-executed`，不记为“新缺陷候选”，更不代表已向维护者验证或上报。

## Dropwise 测试与限制

- 可复跑模型：`cargo test --locked --manifest-path research/phase3/confirmation/Cargo.toml`；16 项都是模型，都要求无取消基线通过、探索穷尽、trial 已取消且不变量失败、没有未实现或未 settle 的计划。额外的 Neon 源码测试在临时 harness 中执行。
- 真实 SCRAM 源码测试是在临时 crate 中运行，使用精确固定 commit 的 sparse checkout 文件；该临时 crate 不提交，固定源码位置、依赖版本、输入和观察结果在本文件记录。
- 16 个模型只保留候选函数中的状态转移、await 前后关系与用于判定的后果；用 `yield_now` 抽象实际 I/O/锁/任务 await，也省略目标项目的并发调用方和完整持久化语义。模型违反不能升级为目标 bug。
- 除 Neon 单模块外，未对目标应用运行构建/集成测试。未做任何 fix-parent A/B，因此目前没有符合预注册标准的新缺陷候选。没有修改 `src/` 或固定快照中的目标代码。
